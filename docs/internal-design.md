# 内部表現と同期の初期設計

更新日: 2026-11-18

ユーザーから委任された設計作業として、[仕様](specification.md)を満たす初期実装の方式をここで選定する。過去の明示合意と、今回選んだ設計判断は区別する。本書は実装仕様の土台であり、実装済み機能・正式な収束証明ではない。

## 1. 選定と範囲

| 領域 | 初期設計 |
|---|---|
| 更新 | 変更不能なレコードの集合。更新IDで重複排除 |
| 項目の版 | 更新IDと項目キーで識別。明示した置き換え対象のグラフ |
| Contentの存在 | 項目とは別の、生存・削除操作のグラフ |
| 操作の基準 | 編集開始時のContent状態を示す固定されたfrontier |
| 現在値 | 更新集合から再構築できる索引。同期する正本ではない |
| 同期 | ノードごとの受理ログを双方向にページ転送 |
| 初回・カーソル無効時 | 全ログを再走査し、既知の更新を重複排除 |
| 履歴削減 | 初期版では行わない。将来は別プロトコルを追加 |

ここでは全Content複製・全履歴保持・信頼済みノードを前提とする。部分同期、無人マージ、履歴削減アルゴリズム、参加証明の暗号形式は範囲外。

## 2. 更新レコード

以下は論理スキーマ。実際のJSON・バイナリ符号化は独立したcodecとして定める。

| フィールド | 内容 |
|---|---|
| format_version | レコードの意味・符号化のバージョン |
| cluster_id | 別クラスタの更新を誤受理しないための識別子 |
| content_id | 永続的なContent ID |
| root_id | このContentを作成した更新ID。作成レコードでは自身のID |
| update_id | 256 bitのランダムID。ノードの連番・時計とは独立 |
| author_node_id | 作成ノード。監査情報であり、因果順序ではない |
| edited_at | Unix epochからの符号付き64 bitのUTCマイクロ秒。通常値選択とContentの最終編集時刻の算出に使う |
| action | create / edit / delete / keep / restore |
| basis | 操作開始時の存在グラフの末端更新ID集合 |
| changes | 項目キー、setまたはunset、値、replacesの集合 |

Node ID、Content IDも独立したランダムIDとし、IDの外部表現は固定長小文字hexを初期案とする。時刻・整数はwire上で精度を落とさない表現を使う。具体codecでは重複キー・不正文字列・整数範囲外等を拒否する。

一つのContentには一つのcreateを認める。同じContent IDに別root_idが届いたら衝突エラーとし、時刻で選ばない。更新の同一性はupdate_idで判定し、同IDの内容不一致は破損・プロトコル違反として停止する。送信元ごとに別の更新として採用しない。

正規化されたレコードbytesとそのdigestを保持する。中継は元のbytesを維持する。digestは同一性検査用で、作成者の署名や正当性の証明ではない。codecとdigest方式は実装前に固定し、相互運用テストを用意する。

### 項目と値

- body: UTF-8テキスト。初期版は本文のunsetを認めず、空本文は空文字。
- attribute(namespace, key): 一つのキー全体が競合単位。JSON相当の値をsetし、unsetは不存在。nullとは別。オブジェクト内の部分更新はしない。
- 配列属性は順序・重複を保持し、配列全体で競合判定する。タグの並行追加も配列二版の競合になり得る。要素単位のsetやlistのマージは行わない。
- kind(name): booleanのset。falseは非所属。unsetは使わない。
- キーは構造化タプルとし、スラッシュを区切った文字列の解釈に依存しない。
- 一つの更新内で同じ項目を複数回変更しない。値の同値比較はcodecの構造的な等価規則を使用する。

初期domain実装では `AttributeValue` を用意した。数値は浮動小数点に変換せず、符号・正規化した10進係数・指数で保持する。`1`と`1.0`は等値、負のゼロとゼロも等値とする。入力指数と正規化後の指数はi64範囲、係数は任意桁とし、サイズ上限はprotocolで定める。オブジェクトはキー順によらず構造比較し、配列は順序と重複を区別する。これは初期実装での選定であり、wire codecと重複キー拒否は未実装。

`Graph::snapshot` は `Content`（ID・本文・属性・kinds）と存在状態・固定basis・値グループごとの版IDを一度の投影で組み立てる。通常値で省かれるunset/falseの版も内部snapshotに保持する。snapshotは所有された値であり、その後の更新受理で編集元を差し替えない。認可・一般アプリ向けの情報制限・編集トークン発行はnode側で追加する。

createは本文と初期属性・kindsを持ち、basisとreplacesは空。未作成の属性は不存在、kindはfalseを既定値とし、既定値そのものには版IDを発行しない。

## 3. 三つの関係を混同しない

### 3.1 basis: 操作が基準にした状態

frontierは、ある依存関係が揃った更新集合の、存在グラフにおける末端集合。その集合からbasisを再帰的にたどった更新集合をC(basis)と呼ぶ。createならCは空。

アプリが取得したスナップショットのfrontierを編集トークンに封入する。保存時に最新frontierへ差し替えない。C(basis)には未解決版も含められるが、それを全部解決する意味ではない。

通常編集でもbasisには削除候補を含められる。ただし、その削除を置き換える権限・意思は別に扱う。kind競合等の非公開情報を含むbasisは不透明なローカルトークンで渡し、ID一覧や内容を一般アプリに公開しない。

### 3.2 項目の置き換え関係

各変更は、同じContent・同じ項目の版をreplacesとして指定する。版は(update_id, field_key)で識別する。参照先はC(basis)内に存在する必要があるが、その時点の末端版でなくてもよい。古い版の編集も有効。

項目fの全版集合をVf、置き換えられた版の集合をSfとすると、現在候補はHf = Vf − Sf。各置き換えレコードも保持するので、祖先は再登場しない。存在グラフで後継になったことだけではHfから版を除かない。

通常編集では、ユーザーが編集した候補の版だけをreplacesに入れる。同じ値の候補をUIで一つにまとめた場合は、その値グループを構成する全版IDを編集元として保持する。別の値の候補は加えない。

未知の属性への最初の追加はreplaces空でよい。既にunsetやfalseの明示版がある場合は、その版を編集元に含める。kind非所属でも、後の追加に使う版情報を内部では失わない。

異なる値が複数残れば項目競合。通常値は現在候補から(edited_at, update_idのbyte順)の最大を選ぶ。同じ値の複数候補は表示上まとめるが、因果情報は残す。時刻を検証時の現在時刻と比較して拒否しない。時計のずれは競合時の表示順位と、選ばれた項目版から計算する最終編集時刻に影響する。

### 3.3 存在の置き換え関係

存在グラフの辺はactionとbasisから決まり、任意の別フィールドとして指定させない。

| action | 新しい存在値 | 存在グラフで置き換える対象 | 項目変更 |
|---|---|---|---|
| create | live | なし | 初期値 |
| edit | live | basis内のlive操作だけ | 指定した項目 |
| delete | deleted | basis全体 | なし |
| keep | live | basis全体 | なし |
| restore | live | basis全体 | 復元スナップショット |

editにはbasis内にlive操作が必要。keepはliveとdeletedの混在、restoreはdeletedのみのbasisに対して使う。deleteは生存・競合・既に削除済みの状態に対して使える。最新状態が変わっていても、固定されたbasisで操作条件を検査する。

存在の全操作から、存在グラフの辺で置き換えられた操作を除いた集合をLとする。Lがliveのみなら生存、deletedのみなら削除済み、混在なら削除競合。複数のdeleteだけなら競合表示は不要だが、全IDを残す。

通常編集はbasisに含まれるdeleted操作を消さない。これにより、削除競合を見た状態で本文だけ編集しても暗黙に「残す」にならない。古いlive状態を基準に保存して、裏で届いたdeleteと競合するケースも同じ規則で扱える。

削除は項目の候補を除去しない。削除済みなら通常Queryから隠し、削除競合なら項目グラフの現在値を表示する。「生存側表示」は特定の端末の完全なスナップショットへ巻き戻す意味ではない。

### 3.4 復元時のリセット範囲

restoreは明示した本文・属性・kindsを、C(basis)に対する復元後の全体として扱う。基準に既知の項目と復元要求に含まれる項目の和集合を列挙し、基準内の項目末端版すべてを置き換える変更へ展開する。

- 本文は必須。
- 省略した既知属性はunset、既知kindはfalse。
- 未知だった項目は、要求に含まれた場合だけ追加する。
- 並行更新で新たに生じた項目や版は置き換えない。

展開済みchangesをレコードに記録し、受信側でもbasisから正しい展開か検査する。受信時点の全キーを列挙してはならない。そうすると到着順で未確認属性が消える。

これは「通常編集の省略は未変更」と異なるrestore専用規則である。未知の並行追加が届けば復元結果にも現れ得る。削除との並行編集は存在グラフでも保持される。

## 4. 妥当性とローカル保存

更新の受理には、root・basis・replacesの全依存が既に受理済みであることを要求する。初期版では子だけを正式受理して後から親を探さない。

検査は以下を含む。

1. バージョン、サイズ、型、ID、クラスタが有効。
2. 同IDは同一レコード。Contentとrootが一致。
3. basisは同じContentの存在グラフ上で相互に祖先でない集合。依存は有限で、自己参照・循環を認めない。
4. actionの条件とchangesの形が一致。replacesはC(basis)内の同じ項目の版。
5. restoreは前節の展開と一致する。

基準が古いことはエラーにしない。依存が不足する場合はMissingDependenciesで再取得し、存在しない参照を空状態として解釈しない。

アプリ保存は次を一つのローカルトランザクションで行う。

1. アプリ資格情報・編集トークン・操作権限を検査する。
2. 現在の通常kindsで変更前のWriteを検査し、候補を仮適用した変更後の通常kindsでも検査する。認可検査とcommitの間に同期更新を割り込ませない。
3. 更新、現在候補、Query用索引、受理ログ、購読用変更記録、再送用結果をcommitする。
4. commit後に保存成功を返し、同期を起こす。

削除前の編集を受け付けるため、既に削除済みの場合の変更前Filterは、保持している項目グラフの通常kindsで評価する。一般Queryで削除済みContentを公開する意味ではない。restoreは初期APIでは全権限の管理ツールに限定し、既存の削除競合のkeep/deleteによる解決も管理ツールで行う。通常のContent削除は従来どおりWriteの範囲で可能。

kind競合は初期版では管理ツール以外へ公開・解決させない。一般アプリが競合中のkindを変更しようとした場合は管理操作が必要な旨を返す。本文・属性の保存を妨げない。ReadなしのWriteへは、別途受け渡された編集トークンを使わせる。トークンはReadやWriteそのものを付与しない。

ローカルの不透明な編集トークンは、固定basis、選択した項目の編集元、用途をサーバー側に保持する方式から始める。再起動後も利用できるよう永続化する。トークンを失った場合は再取得を要求し、勝手に最新状態を編集元にしない。トークンのGC・移植は別途設計する。

### アプリ要求と同期更新の二種類の再送

- アプリはノード内で一意なrequest_idを付ける。同じapp_id・request_id・同じ要求なら、再保存せず元のupdate_idと保存結果を返す。別要求への使い回しはエラー。初期版は対応表を保持する。
- 同期はupdate_idで重複排除する。既知の同一更新に新しい受理ログ番号を付けない。
- アプリ再送の対応表はローカル認可情報とともに同期対象外。同じ要求を別ノードへ送り直すときのexactly-onceは保証しない。
- 再送でも現在のアプリ認証を行う。以前の結果を返すために権限外の本文を再公開しない。

## 5. 保存構造

初期の論理テーブル案。物理DB・索引の最適化は計測後に行う。

| テーブル | 主な内容 | 再構築 |
|---|---|---|
| updates | 不変bytes、ID、Content、digest、作成元 | 正本 |
| dependencies | basisと項目参照 | updatesから可能 |
| field_versions / field_heads | 値・replaces・現在候補 | updatesから可能 |
| life_edges / life_heads | 存在の置き換え関係・末端 | updatesから可能 |
| content_view | 通常本文・属性・kinds・競合・生存状態 | updatesから可能 |
| accept_log | local_seq → update_id | 再構築時はepoch変更 |
| peer_cursors | 相手Node ID・相手log_epoch・受理済みseq | 消失時は再走査 |
| edit_tokens / request_results | ローカル編集状態・要求の再送結果 | 同期対象外 |

受理ログには、依存レコードより後に子を追加する。seqは単調増加し、ロールバック等の欠番を許す。数値の連続性ではなく、ログの順序とページ境界を使う。ログは初期版では削減しない。

現在候補は単に「親を消して自分を追加」するだけでも依存順の受理なら更新できる。索引再構築は必ず依存順で実行する。依存の壊れたレコードを無視して現在値だけ作らない。

## 6. 同期プロトコル

### 6.1 接続とカーソル

相手ノードの認証とクラスタ参加資格を検査してからデータを扱う。HTTPSとirohで同じ論理プロトコルを使う。

Handshakeはプロトコルバージョン、レコード形式、Cluster ID、Node ID、log_epoch、現在の上限seq、受理可能サイズを交換する。対応形式が合わなければ明示的に停止し、未知フィールドを捨てて既知形式へ変換しない。

受信側が持つカーソルは(sender_node_id, sender_log_epoch, accepted_seq)。accepted_seqは、その送信者のログをその位置まで欠落なく受理したことを示す。作成元の連番・全クラスタの進捗ではない。

log_epochはログの番号付けの世代を示すランダムID。通常再起動では維持し、ログの再構築時は必ず変更する。古いバックアップ復元は仕様どおり新Node IDで再参加する。カーソルだけを復元して、データがないのに受理済みと主張しない。

### 6.2 一方向の転送

1. 受信側のカーソルを確認する。初回は0。
2. 送信側はその時点の上限Hを固定する。
3. after < seq <= Hの先頭から、サイズ制限内のページを返す。
4. 受信側はページ全体を検証し、依存順に一つのトランザクションで受理する。
5. 更新・索引・受理側のログ・送信者に対するカーソルを同時commitしてからACKする。
6. Hまで終えたら、この方向のこの上限までの転送完了。新着は次のラウンドで取得する。

ページはepoch、after、through、H、seq付きレコード列を持つ。送信側は範囲内のレコードを省略しない。通常throughは最後に含めたseq。範囲が空ならthrough=Hにできる。受信側はafterが現在カーソルと一致すること、順序、範囲、上限を検査する。信頼済み送信者がログを隠さないことは前提であり、seqの欠番から改ざんを暗号学的に検出する設計ではない。

初期版はページ単位で全成功か全失敗とする。途中に不正・未対応・依存不足の更新があればページをrollbackし、カーソルを進めない。容量不足も同じ。エラーには失敗したIDと理由を含め、無制限に高速再送せず、修復・更新を待つ。問題更新を黙って飛ばす機能は持たない。

依存は送信ログの先行位置にあるので、正常な初回走査では欠けない。欠けた場合はID指定で依存を取得し、祖先から受理する。この個別取得はストリームカーソルを飛び越して進める根拠にはしない。供給側にも依存がないなら破損として停止する。

### 6.3 双方向とHTTP

端末AからHTTPノードSへ一回接続した場合も、同じ二本の転送を行う。

- A→S: Sが保持するAのカーソルを問い合わせ、Aのログページをアップロードする。ACKはSのcommit後。
- S→A: Aが保持するSのカーソルを指定し、Sのログページをダウンロードする。Aはcommit後に受領を伝える。

SからAへの新規接続は不要。二方向を小さいページで交互に進め、一方の新着で他方を飢餓状態にしない。各方向のHを固定するので、継続的な保存があってもそのラウンドは終了する。

受信した更新も受理側のログに追加されるため、A→S→Bと伝播する。A自身へ戻ってもupdate_idで既知と判定し、新しいログ行や変更通知を生成しない。ログ位置に対するカーソルは重複ページでも正常に進める。

同じ相手・方向・epochの転送は一つに直列化する。別接続による古いafterの要求には現在カーソルを返して再開させる。異なる相手からの重複受信はDBの更新ID一意制約と同一bytes検査で処理する。

### 6.4 切断・クラッシュ・再送

| 障害 | 結果 |
|---|---|
| commit前に受信側停止 | ページとカーソルをrollback。再送 |
| commit後、ACK前に切断 | カーソル照会で続行、または同じページを再送。重複更新なし |
| 送信側がACKを忘れる | 受信側の永続カーソルを再確認 |
| 受信側カーソルのみを失う | 0から再走査。既知IDで重複排除 |
| ログepoch変更 | 古いカーソルを拒否し0から再走査 |
| 相手が未対応形式を含む | そのページで停止し、明示エラー |
| 保存容量不足 | ACKせず停止。送信側のデータを保持 |

ACKは「そのノードがその時点で永続化した」という意味。他ノードへの複製や将来のバックアップ耐久性を保証しない。受領報告がないだけで、未保存と断定もしない。

### 6.5 通知と定期照合

ローカル保存・新規受理後に同期処理を起こす。通知には内容を載せなくてもよく、上限seqが進んだことだけでよい。通知欠落は次の定期照合で回収する。

変更なしならepochと上限の比較だけで終える。相手ごとに指数的な再試行間隔とjitterを使い、復帰・ネットワーク変更・手動操作で早めに再試行する。具体的な時間とページサイズは運用パラメータ。

最初は全レコードをページで運ぶ。単一更新が上限を超える場合は明示拒否し、途中まで保存しない。上限はクラスタの互換性条件として合わせる。将来の大容量対応はレコード本体の分割転送を追加し、commit単位は変えない。

## 7. 認可・参加情報との境界

アプリの権限検査は作成ノードのローカル保存で行う。同期受理時に、そのアプリの認可を再現したり現在のkindsで過去更新を拒否したりしない。受信側は認証済みの信頼済み相手と、更新の構造・依存・意味を検査する。

初期設計では各データ更新への作成者署名は必須にしない。信頼済みノードの中継を信頼するため、author_node_idは悪意ある参加ノードに対する証明ではない。悪意ある参加ノードへの耐性は保証しない。

退役した作成元の既存データは消さず、現在信頼する相手から中継される過去レコードもauthorだけで拒否しない。退役は接続・参加資格の問題であり、過去データの取消しではない。

参加・退役証明の交換はデータ転送より前の管理経路として別管理する。不正なContentレコードでデータストリームが止まっても、退役情報の伝播まで止めない。管理経路の証明形式と、退役と並行する承認の検証規則は別途必要で、本書だけでネットワーク公開可能な認証設計が完成したとはしない。

## 8. 履歴削減と復旧の境界

初期版の正しさは、全依存レコードが残ることに依存する。これは全履歴の永久保持を外部契約にする意味ではない。

将来本文を削減するには、少なくとも項目と存在の因果情報、現在候補、削除記録、旧更新の重複識別を保つチェックポイント形式が必要。圧縮済みノードからの初回同期・古い編集元の検証・古いノードの復帰を新プロトコルで設計する。値を消すだけのGCを初期版へ追加しない。

その際、保持範囲より古いカーソルにはSnapshotRequiredを返す等の拡張を想定するが、snapshot形式は未設計。現在値だけのコピーでは競合・削除を安全に復元できない。初期版のepoch変更による全ログ再走査と、将来の圧縮後復旧を混同しない。

exportは通常値・未解決版・削除記録・因果情報を区別して出す。importを作る際には、元IDを維持した復旧と新しいContentとしての取込みを別モードで検討する。ローカルアプリ認可や管理秘密鍵は自動復旧しない。

## 9. 検証と実装順序

意味モデルの検証コードを[design_checks/model_check.py](../design_checks/model_check.py)に置く。小さい更新集合について到着順・再送を変え、依存が揃ったときにだけ受理するモデルを検査する。実際のDB・通信・暗号実装のテストではない。

検証対象は、通常の本文競合、解決中の追加更新、項目別編集、kindの同値追加と削除、削除競合中の通常編集、keepとdelete、並行restore、復元での既知属性削除と未知属性保持、時計逆転、重複・同ID不一致、ページ失敗とACK喪失。

実装順序は、純粋な更新検証・状態計算、永続化とアプリ保存、双方向ログ転送、HTTP/irohアダプタ、管理経路の順を基本とする。ネットワーク公開は管理経路と相手認証が完成してから行う。

codec・数値表現・サイズ上限の初期実装は[record v1](../contracts/record-v1.md)を参照。管理証明、OS別資格情報保護、将来のチェックポイントは未固定。グラフの意味とログ同期の方式はこの設計を出発点として実装・検証を進める。
