# Mote — 要件定義 v0.2

2026-11-26

## 1. 概要

### 1.1. プロダクト名

**Mote**

小さな粒子や断片を意味する英単語に由来する。思考や外部情報の断片を捕捉し、Harmionに取り込むアプリケーションである。

### 1.2. 目的

Harmionをバックエンドとする個人用の汎用情報Captureアプリを開発する。

現在、DiscordのサブアカウントへのDMを利用して行っている情報や思考の記録を置き換えることを主な目的とする。

短いメモ、外部から共有された情報、長時間の独り言による思考などを、可能な限り少ない操作でHarmionに取り込めるようにする。

### 1.3. プロダクトの責務

Moteは恒久的な知識ベースではなく、情報が整理されるまでの中間的なInboxである。

主な責務は以下に限定する。

- 情報のCapture
- 音声認識
- 記録内容の永続化
- LLMによる意味的な整形・分割
- 記録内容の閲覧
- Inboxの管理

最終的な情報の整理、知識の蓄積、高度な編集については、Wikiなどの他のアプリケーションに委譲する。

Moteは情報の整理先や、整理先における処理結果を認識・管理する必要はない。

### 1.4. 設計原則

- 可能な限り少ない操作で情報を記録できること。
- 入力時に情報の分類や整理を強制しない。
- 入力時の区切りと、情報としての意味的な区切りを分離する。
- 思考や入力を中断させないことを優先する。
- Captureと最終的な情報整理を分離する。
- LLMなしでも基本機能が成立すること。
- 元の記録をLLMによって破壊的に変更しない。
- 主なユーザーは開発者自身であるため、過剰な汎用化やカスタマイズ機能を要求しない。
- 実装上の拡張性は確保する。

## 2. 入力方式

### 2.1. 短文Capture

ホーム画面下部に、Discordなどのチャットアプリに近い入力欄を設ける。

- テキストや音声による短い入力を即座に保存できる。
- 一回の短文Captureは、原則として意味的に一つのまとまりを持つ。
- 一回のCaptureを一つのHarmion Contentとして保存する。
- タイトルや分類の入力を強制しない。
- LLMによる整形は手動実行を基本とする。
- 入力確定前のテキストは編集可能とする。

### 2.2. 長文Capture

ホーム画面の入力欄に設けた拡大ボタンやジェスチャーなどから、専用の長文Captureビューへ遷移する。

- 一つのセッション内で複数回の音声・テキスト入力を行える。
- 入力内容は同一のHarmion Contentに順次追記する。
- セッションの中断と再開に対応する。
- 画面から離れることによってセッションを終了しない。
- セッションはユーザーによる明示的な完了操作によって終了する。
- 複数の長文セッションを並行して進行させる機能は、初期実装では必須としない。

長文Captureにおける各入力の区切りは、必ずしも意味的な区切りではない。

時間的制約、入力方法、思考途中の中断など、その場の事情によって分割されることを想定する。

一つの長文セッション内で複数の話題が混在することを許容する。別のアイデアを思いついた場合も、新規セッションを開始する必要はない。

意味的な分割や構造化は、セッション完了後にLLMを利用して行う。

### 2.3. 音声入力・音声認識

ストリーミング方式の音声認識を採用する。

- 認識結果を入力中に逐次表示する。
- 沈黙や言い淀みによって入力セッションを自動終了しない。
- ユーザーによる明示的な操作によって音声入力を終了する。
- 入力中の手動編集は最小限とし、思考への集中を優先する。
- 長時間の連続した音声入力に対応する。
- 音声認識エンジン内部の発話区間と、Captureとしての記録単位を分離する。
- 長文Captureでは、音声認識結果がある程度確定した時点で、Harmionへの書き込みを順次行う。
- 短文Captureにおいては、認識途中の分割によって複数のContentが生成されないようにする。

音声認識はローカル処理を優先し、可能な限り無料で運用できるようにする。

ただし、クラウドベースの音声認識についても、認識精度、処理速度、費用、端末負荷によっては採用を検討する。

### 2.4. バックグラウンド音声認識

**アプリの画面を離れても音声認識を継続できることを必須要件とする。**

具体的には以下の動作を要求する。

- 他のアプリを操作しながら音声認識を継続できる。
- 画面消灯中・端末ロック中も音声認識を継続できる。
- Moteに戻った際に、それまでの認識結果を確認できる。
- Androidの通知から音声認識を停止できる。
- Activityのライフサイクルに音声認識のライフサイクルを依存させない。
- 画面遷移やActivityの再生成によって認識セッションを失わない。
- OSによる強制終了などが発生した場合も、可能な限り確定済みの入力内容を失わない。
- 音声認識中であることをユーザーが確認できる。

Captureセッション、音声認識セッション、UIのライフサイクルは、それぞれ独立したものとして設計する。

Androidにおいては、microphoneタイプのForeground Serviceを利用する構成を有力候補とする。

OSによる強制停止など、プラットフォーム上回避できない制約については、復旧可能性を重視する。

### 2.5. 元音声の保持

音声認識に使用した元音声は、端末内に一定期間保持する。

主な目的は以下の通り。

- 音声認識失敗時の復旧
- アプリの異常終了からの復旧
- 必要に応じた再認識
- 音声認識エンジンの評価・比較

元音声を恒久的に保存することは目的としない。

- 一定期間経過後に自動削除する。
- Harmionには同期しない。
- Moteのローカルストレージに保存する。
- 未確定・未復旧の入力に必要な音声は、自動削除の対象から除外することを検討する。

具体的な保存形式、保持期間、容量上限は未決定。

### 2.6. Android共有メニュー

Androidの共有メニューからMoteを呼び出せるようにする。

初期実装で受け付けるデータは以下に限定する。

- テキスト
- URL

共有先としてMoteを選択すると、通常の短文Captureに近い簡易入力欄を表示する。

共有された内容にコメントなどを追記し、保存できるようにする。

以下は初期実装の対象外とする。

- 外部から共有された音声ファイル
- 画像
- OCR
- その他のファイル
- ウィジェット経由の入力

## 3. UI / UX

### 3.1. デザイン方針

- Material 3 Expressiveをベースとする。
- ホーム画面はDiscordなどのチャットアプリに近い構造とする。
- スワイプ操作やInboxの管理についてはSparkを参考にする。
- 既存アプリのUIを直接模倣することは目的としない。
- 情報密度と入力の容易さを重視する。
- 頻繁に使用する操作は、可能な限り片手でアクセスしやすい位置に配置する。
- Mote独自の可愛らしさや遊び心を、モーションや細部のデザインに取り入れることを検討する。
- 不必要な装飾や、入力・閲覧を妨げる演出は避ける。

### 3.2. ホーム画面

未アーカイブのCaptureを表示するInbox型の画面を基本とする。

- Captureを時系列順に表示する。
- 古いCaptureを上、新しいCaptureを下に配置する。
- デフォルトではInboxを表示する。
- アーカイブ済みを含むすべてのCaptureにも容易にアクセスできる。
- 画面最下部に短文Capture用の入力欄を設ける。
- 入力欄から長文Captureビューへ移行できる。
- Inbox / Allの切り替えとPinnedフィルターを入力欄の直上に配置する。
- フィルター類は親指で操作しやすいように右寄せする。

概念的な画面構成：

```
┌─────────────────────────────┐
│ Mote                        │
├─────────────────────────────┤
│                             │
│ 古いCapture                 │
│                             │
│ Capture                     │
│                             │
│ Capture                     │
│                             │
│ 最新のCapture               │
│                             │
├─────────────────────────────┤
│        Inbox / All   Pinned │
├─────────────────────────────┤
│ 入力欄         拡大 音声 送信 │
└─────────────────────────────┘
```

具体的なレイアウト、コンポーネントの形状、各ボタンの配置は実装・実機検証を通じて調整する。

### 3.3. フィルター

Inbox / Allの切り替えとピン留めフィルターは独立させる。

表示状態は以下の四つとなる。

| フィルター | 表示対象 |
|---|---|
| Inbox | 未アーカイブのCapture |
| All | すべてのCapture |
| Inbox + Pinned | 未アーカイブかつピン留めされたCapture |
| All + Pinned | アーカイブ状態を問わずピン留めされたCapture |

ピン留めによって通常の時系列順を変更しない。

### 3.4. スワイプ操作

左右のスワイプを頻繁に使用する二つの操作に割り当てる。

暫定的な操作体系：

| 操作 | 機能 |
|---|---|
| 左スワイプ | アーカイブ／アーカイブ解除 |
| 右スワイプ | LLM整形 |
| タップ | 詳細表示 |
| 長押し | コンテキストメニュー |

コンテキストメニューには以下の操作を配置する。

- ピン留め／解除
- コピー
- 共有
- 削除
- その他、必要な補助操作

具体的なスワイプ方向、閾値、アニメーションについては実機で調整する。

削除はスワイプ操作に割り当てない。

### 3.5. 誤操作の防止

アーカイブと削除を明確に区別する。

アーカイブ：

- 確認ダイアログを要求しない。
- 即座に実行する。
- Snackbarなどを利用して直後に取り消せるようにする。

削除：

- コンテキストメニューや詳細ビューから実行する。
- 明示的な確認操作を要求する。
- 削除対象と、連鎖削除される派生Contentの範囲を表示する。
- 誤操作によって即座に削除されることを防止する。

Mote独自のゴミ箱機能は必須としない。復元については、Harmion側の履歴・復元機能を利用できるか検討する。

### 3.6. 個別Captureビュー

各Captureは専用の詳細ビューを持つ。

主な機能：

- 記録内容の閲覧
- テキストの選択・コピー
- LLM整形の実行
- 再整形
- 派生Contentの参照
- 派生Contentから元Captureへの参照
- アーカイブ
- ピン留め
- 削除
- OS標準の共有機能

確定済みContentの編集機能は、初期実装では必須としない。

### 3.7. 長文Captureビュー

- メッセージアプリのスレッドに近いUIとする。
- 各入力を個別のメッセージのように表示してもよい。
- 音声とテキストによる入力を繰り返せる。
- 一連の入力を一つのCaptureセッションとして扱う。
- 中断後も入力を再開できる。
- 音声認識を継続したまま他のアプリへ移動できる。
- セッションを明示的に完了する操作を設ける。

UI上のメッセージ単位と、Harmion上のContent単位は一致する必要がない。

入力単位の境界を厳密に復元できることも必須としない。

### 3.8. 完了アニメーション

長文Captureの明示的な完了時に、短く可愛らしいアニメーションを表示することを検討する。

Moteという名称に由来する粒子や断片などを、デザインモチーフの候補とする。

- Captureの保存完了を表現する。
- LLM整形の完了を待たない。
- 次のCaptureを妨げない。
- 長時間の演出や追加操作を要求しない。
- 具体的な演出はデザイン段階で決定する。

### 3.9. 編集機能

Moteを本格的なエディタとして設計しない。

| 対象 | 編集方針 |
|---|---|
| 入力確定前 | 編集可能 |
| 進行中の長文Capture | 追記可能 |
| 確定済みの元Capture | 原則として編集しない |
| LLMによる派生Content | 原則として編集しない |

高度な編集機能、タグ管理、フォルダ管理、知識ベースとしての管理機能は要求しない。

## 4. Harmionとの統合

### 4.1. 責任分界

MoteはHarmionのクライアントアプリとして動作する。

- Android版Harmionを通じてContentの作成・更新・取得・削除を行う。
- 同期スケジュール、ネットワーク通信、端末間同期などはHarmion側に委譲する。
- Mote独自の端末間同期システムは持たない。
- Mote側はContentを更新するタイミングを決定する。
- ローカルに保持する音声や未確定入力、実行中の処理などはMote側で管理する。

### 4.2. Contentの粒度

一つのCaptureセッションを一つのContentとして保存する。

短文Captureの場合、一回の入力が一つのContentに対応する。

長文Captureの場合、複数回の入力を一つのContent内に保持する。

```
Capture Content
├── Input 1
├── Input 2
├── Input 3
└── Input 4
```

長文Captureにおける各入力は、意味論的に独立した情報とは限らないため、個々の入力を別Contentとして保存しない。

### 4.3. Content本文の形式

元Capture、派生Contentともに通常のテキストを本文として保持する。

長文Captureでは、入力内容を同一Contentに順次追記する。

入力単位の区切りは、空行などの軽量な表現で十分とする。

以下は要求しない。

- 入力単位の厳密な識別子
- 入力境界の完全な復元
- 本文全体のJSONによる構造化
- 入力ごとの詳細なメタデータ管理

具体的な区切り形式は実装時に決定する。

### 4.4. Kind

Capture専用の`capture` Kindを定義する。

Kindは、Contentを解釈・利用するアプリケーションやInterpreterとの契約であると同時に、現行Harmionにおけるアクセス制御にも利用される。

- 元Captureには`capture` Kindを付与する。
- LLMによって生成された派生Contentにも、初期状態では`capture` Kindのみを付与する。
- LLM整形によって`wiki`などのKindを自動的に付与しない。
- Moteは原則として`capture` Kindに必要な権限のみを要求する。
- Wikiアプリの権限をMoteとの連携だけを目的として拡大する必要はない。
- Harmion全体のKindベースのアクセス制御を尊重する。
- `capture`と他のKindが共存できるというHarmionの既存の設計は維持する。

Mote内でのKind変更や他のKindへの移管機能は、初期実装では要求しない。

### 4.5. Attribute

以下の永続的な情報をAttributeによって管理する。

- アーカイブ状態
- ピン留め状態
- 長文Captureの進行・完了状態
- 元Contentと派生Contentの参照関係
- 必要に応じたCaptureの来歴
- 必要に応じたLLM整形状態

Attributeの暫定的な表現例：

```json
{
  "capture": {
    "archived": false,
    "pinned": false,
    "session_open": false,
    "derived_from": null
  }
}
```

これは確定したスキーマではない。

具体的な名称、型、名前空間、デフォルト値、状態の表現方法については、既存のHarmionの実装を確認した上で決定する。

整形済み状態など、他の情報から導出可能な状態については、不必要な重複保存を避ける。

音声認識中、LLM実行中、未確定入力などの一時的な実行状態をHarmionのAttributeとして保存する必要はない。ただし、異常終了からの復旧に必要な情報はローカルに永続化してよい。

### 4.6. バイナリデータ

現時点のHarmionではテキストデータのみ同期できる。

元音声などのバイナリデータはMote側で端末内に保存する。

将来的なHarmionのバイナリデータ対応を妨げない設計とする。

## 5. Captureのライフサイクル

### 5.1. 短文Capture

```
入力開始
    ↓
テキスト・音声入力
    ↓
入力確定
    ↓
HarmionにContentを作成
    ↓
Inboxに表示
```

LLM整形は必要に応じて手動で実行する。

### 5.2. 長文Capture

```
セッション開始
    ↓
入力・音声認識
    ↓
確定した内容をHarmionに順次書き込み
    ↓
入力・中断・再開を繰り返す
    ↓
明示的な完了操作
    ↓
残りの入力を確定・永続化
    ↓
セッション終了
    ↓
完了アニメーション
    ↓
ホーム画面へ戻る
    ↓
バックグラウンドでLLM整形
```

自動整形が無効の場合は、LLM整形を実行しない。

長文Captureの終了と、音声認識の終了は独立した操作とする。

音声認識を停止しても、Captureセッションは継続できる。

### 5.3. 永続化

長文Captureでは、セッション完了時まで入力をメモリ上に保持する設計を採用しない。

テキスト入力が確定した場合や、音声認識によってある程度まとまったテキストが確定した場合には、Harmionに順次書き込む。

Harmionへの書き込みが失敗した場合も、未保存の入力を失わないようにする。

Harmionへのローカル書き込みの成功と、他端末への同期完了は区別する。Moteは原則として端末間同期の完了を待つ必要はない。

## 6. LLMによる整形

### 6.1. 目的

音声入力や長文Captureでは、以下の情報が混在することを想定する。

- 音声認識の誤り
- 言い淀み
- 重複
- 言い直し
- 撤回された発言
- 思考途中の仮説
- 条件付きの結論
- 複数の独立した話題

これらを後から利用しやすい形に整えるためにLLMを利用する。

LLM整形の目的は、単純な要約ではなく、意味を保存した正規化と意味的な分割である。

### 6.2. 処理内容

- 音声認識の誤認識の修正
- 言い淀みや重複の整理
- 文章の整形
- 混在した話題の分離
- 話題ごとの情報の構造化
- 仮説、確定事項、未決定事項などの区別

ユーザーの発言の意味、条件、不確実性を不必要に変更しない。

情報を短くすること自体を目的としない。

### 6.3. 処理範囲

一回のCaptureセッション内で処理を完結させる。

以下はMoteのLLM整形機能の責務に含めない。

- 過去のCaptureを横断した情報の統合
- Wiki全体を参照した情報の整理
- 継続的な知識ベースの管理
- 外部情報の自動調査
- 最終的なKindの分類
- Wikiなどへの自動的な書き出し

### 6.4. 実行タイミング

短文Capture：

- 手動実行を基本とする。
- 不必要なLLM処理を行わない。

長文Capture：

- 明示的なセッション完了時に自動整形を行う。
- 自動整形を設定によって無効化できる。
- セッション進行中は整形を行わない。

処理は非同期で実行し、通常のCapture操作や次のセッションの開始を妨げない。

LLM整形に失敗しても、Captureそのものの保存結果には影響を与えない。

### 6.5. 派生Content

元のCapture ContentをLLMによって直接上書きしない。

整形結果は独立したContentとして保存する。

一つの元Contentから、意味的に独立した複数の派生Contentを生成できる。

```
Raw Capture Content
├── Derived Content A
├── Derived Content B
└── Derived Content C
```

各派生Contentは参照Attributeによって元Contentを参照する。

- 元の文字起こしや入力内容を保持する。
- 派生ContentのKindは原則として`capture`のみとする。
- 派生Contentは中間データとして扱う。
- 派生Content自体を高度に編集することは想定しない。
- 派生Contentから元Captureを確認できるようにする。

### 6.6. 整形後のInbox

整形によって生成された派生Contentは、Inboxに独立した項目として表示する。

元Captureと派生Contentを常に一つのグループとして表示する必要はない。

整形精度が十分である場合には、整形成功後に元Captureを自動アーカイブする運用を想定する。

ただし、現時点ではLLMの実際の整形精度が未知数であるため、自動アーカイブの採否・デフォルト設定については実際の整形結果を評価した上で決定する。

元Captureはアーカイブ後もAllおよび派生Contentから参照できる。

### 6.7. 再整形

同じ元Captureに対して複数回の整形を実行できる。

再整形は以下の二つの方式に対応する。

**置換**

- 既存の派生Contentを新しい整形結果で置き換える。
- 十分な整形精度が得られる場合の基本的な挙動とする。

**保持・追加**

- 既存の派生Contentを保持したまま、新しい整形結果を追加する。
- 異なるモデルやプロンプトによる結果の比較などに利用する。

いずれの場合も元Captureを変更しない。

置換時には、新しい派生Contentの保存がすべて成功する前に既存の派生Contentを削除しない。

本格的な世代管理や意味的な差分更新は、初期実装では要求しない。

### 6.8. LLMバックエンド

以下の選択肢を検討する。

- スマートフォン上のローカルLLM
- クラウドベースのLLM

評価基準：

- 整形精度
- 意味の保存
- 情報の網羅性
- 費用
- 処理速度
- 端末負荷
- プライバシー

LLMバックエンドとMote固有の整形ロジックは分離する。

外部サービスを利用する場合は、データの送信先や送信条件を適切に制御できるようにする。

モデル、プロンプト、構造化出力形式、リトライ方式は未決定。

### 6.9. 整形精度の評価

実際のCaptureデータを利用して、LLMの整形精度を評価する。

特に以下を重視する。

| 評価項目 | 優先度 |
|---|---|
| 情報の欠落を防ぐ | 最重要 |
| 発言の意味を保存する | 最重要 |
| 仮説と確定事項を区別する | 高 |
| 発言の撤回や修正を適切に扱う | 高 |
| 条件や不確実性を保存する | 高 |
| 話題を適切に分割する | 高 |
| 音声認識の誤りを修正する | 高 |
| 文章の読みやすさ | 中 |
| 文章の短さ | 低 |

## 7. 情報管理

### 7.1. Inboxとアーカイブ

Inboxには未アーカイブのCaptureを表示する。

アーカイブによってInboxから取り除ける。

- アーカイブ済みのCaptureも引き続き閲覧できる。
- アーカイブ状態とLLM整形状態は独立させる。
- アーカイブ状態とピン留め状態は独立させる。
- LLM整形の完了をアーカイブの必須条件にしない。
- アーカイブ解除によってInboxへ戻せる。

アーカイブは基本的にユーザーによる独立した操作とする。

コピー、共有、Wikiの編集などに伴って自動的にアーカイブする必要はない。

整形成功後の元Captureの自動アーカイブについてのみ、別途検討する。

### 7.2. ピン留め

Captureを優先的に処理したい場合にピン留めできる。

- ピン留め状態はAttributeとして保持する。
- 通常の時系列順を変更しない。
- ピン留めされたCaptureには視覚的な識別表示を設ける。
- アーカイブによってピン留めを自動解除しない。
- Inbox / Allとは独立したPinnedフィルターによって絞り込める。

ピン留めされたContentを常時オーバーレイ表示したり、一覧の特定位置に固定したりする必要はない。

### 7.3. 削除

削除操作の意味を操作元によって区別する。

Moteから元Captureを削除した場合：

- 元Contentを削除する。
- 関連する、Moteの管理下にある派生Contentも削除する。
- 削除前に対象範囲を明示する。

Harmion本体の通常の削除操作で元Contentを削除した場合：

- 元Contentのみを削除する。
- 派生Contentは自動的に削除しない。

Harmion本体におけるContent間の参照関係は、一般的な所有関係を意味しない。

連鎖削除はMote固有のドメインロジックとして実装する。

派生Contentのみを削除する場合には、原則として元Captureを削除しない。

Wikiなどに独立して作成されたContentは、元Captureの削除や再整形の影響を受けない。

派生Content自体に他のKindが付与された場合の扱いや、連鎖削除の厳密な判定条件は実装時に決定する。

### 7.4. 検索

高度な検索機能は初期実装では必須としない。

Moteが恒久的な知識ベースになることを目的としないため、検索の実装優先度は比較的低い。

必要に応じて基本的なテキスト検索を追加する。

## 8. 他のアプリケーションとの連携

### 8.1. 基本方針

Moteは情報の最終的な整理先を管理しない。

ユーザーはMoteを参照しながら、Wikiやその他のアプリケーションにおいて必要な情報整理を行う。

整理が完了したCaptureについては、Mote上で個別にアーカイブする。

Moteに以下の機能を要求しない。

- Wiki専用の書き出し機能
- Wiki Contentとの対応関係の管理
- 既存Wikiへの自動マージ
- Kindの自動変更
- 他のアプリケーションにおける整理状態の追跡

テキストのコピーやOS標準の共有機能は、汎用的な補助機能として提供する。

### 8.2. Linux / CLI

デスクトップ環境からCaptureを確認・整理できるようにするため、Linux向けのCLIを提供することを検討する。

主な機能：

- Inboxの一覧表示
- 全Captureの一覧表示
- ピン留めによる絞り込み
- Content本文の取得
- アーカイブ／アーカイブ解除
- ピン留め／解除
- 必要に応じた検索

想定するコマンドの例：

```sh
mote list
mote list --all
mote list --pinned
mote show <id>
mote show <id> | wl-copy
mote archive <id>
mote unarchive <id>
mote pin <id>
mote unpin <id>
```

具体的なコマンド体系は未決定。

既存のFuzzy Finderやエディタなどと組み合わせられるように、一般的なCLIインターフェースを優先する。

CLIからCaptureを閲覧しながら別のアプリケーションで情報を整理し、その後CLIからアーカイブする運用を想定する。

専用のデスクトップGUIは初期実装では要求しない。

## 9. 信頼性

### 9.1. 異常終了への対応

長時間の音声入力やバックグラウンド動作を想定するため、異常終了によるデータ損失を可能な限り防止する。

- 確定済み入力を順次永続化する。
- Harmionへの書き込みに失敗した入力を保持する。
- 必要に応じてローカルに復旧用データを保持する。
- 長文Captureの中断後に再開できるようにする。
- Activityの再生成によって音声認識セッションを失わない。
- 元音声の一時保存を復旧に利用できるようにする。
- 実行中の処理と永続化されたContentの状態を区別する。

### 9.2. 競合処理

端末間の同期や一般的なContentの競合処理は、原則としてHarmionの既存仕様に従う。

ただし、同じ長文Captureが複数端末から同時に更新された場合には、後勝ちによって入力が失われる可能性がある。

これについては既存のHarmionの更新・履歴管理の仕様を確認し、必要な制約や復旧方法を実装時に決定する。

### 9.3. LLM整形中の更新

LLM整形は特定時点の元Captureを入力として実行する。

整形処理中に元Contentが更新された場合、古い入力に対する整形結果をどのように扱うかについては、明示的な方針を設ける。

Contentのリビジョンや本文のハッシュを利用した検証などを候補とする。

具体的な実装方式は未決定。

### 9.4. 部分的な失敗

以下の操作では複数のContentを更新する可能性がある。

- LLM整形による複数の派生Contentの生成
- 再整形による既存結果の置換
- 元Captureと派生Contentの連鎖削除
- 整形成功後の元Captureのアーカイブ

これらの操作について、部分的な失敗や途中でのプロセス終了に対応する。

HarmionのAPIが提供する原子性や更新保証を確認した上で設計する。

少なくとも、整形失敗によって元Captureが失われたり、再整形失敗によって既存の整形結果が不必要に失われたりすることを防止する。

## 10. 実装アーキテクチャ

### 10.1. Android技術スタック

Jetpack ComposeおよびMaterial 3 Expressiveを有力候補とする。

既存のAndroid版Harmionの構成や利用可能なAPIを確認した上で、具体的な技術スタックを決定する。

### 10.2. 責務の分離

以下の責務を独立して扱える構成とする。

- UI
- Captureセッション管理
- Harmionとの接続
- 音声入力
- 音声認識

- LLMバックエンド

- バックグラウンド処理
- 復旧処理

これらを必ずしも個別のビルドモジュールに分割する必要はない。具体的なモジュール構成は実装時に判断する。

### 10.3. 音声認識のアーキテクチャ

UIとは独立した音声認識の実行環境を設ける。

概念的な構成：

```
Compose UI
    ↕
Capture Session Controller
    ↕
Background Recognition Service
    ├── Audio Input
    ├── Audio Storage
    ├── ASR Engine
    └── Transcript Buffer
              ↓
          Harmion Client
```

Android Foreground Serviceを有力候補とする。

音声認識エンジンは交換可能な構造とする。

Android標準の音声認識APIを利用する場合も、長時間のストリーミング認識やバックグラウンド動作の要件を満たすか検証する。

### 10.4. LLM処理のアーキテクチャ

LLMバックエンドとMote固有の整形処理を分離する。

概念的な構成：

```
Raw Capture
    ↓
Tidy Pipeline
    ├── Prompt Construction
    ├── LLM Backend
    ├── Structured Output Parsing
    └── Output Validation
    ↓
Derived Contents
    ↓
Harmion
```

ローカル・クラウドのバックエンドを交換可能にする。

ユーザー向けGUIで任意の処理パイプラインを構築する機能は要求しない。
