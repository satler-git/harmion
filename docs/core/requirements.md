# Harmion — 現時点の仕様と設計方針

更新日: 2026-11-18

この文書は設計合意のスナップショットであり、実装済み機能の説明ではない。最新のユーザーの訂正・承認を優先し、通信形式・内部データ構造などの例示を確定仕様として扱わない。

確認範囲は、文書作成時の会話全文として提供された範囲、同会話に挿入された過去チャットの抜粋・引き継ぎ、およびプロジェクトの会話要約。省略された過去チャットの原文すべてを確認したものではない。照合結果と未解決の境界は [review.md](../records/review.md) を参照。

## 1. 目的・前提

- 一人のユーザーが一つのクラスタを所有する、個人データ基盤。
- アプリを交換してもデータを維持でき、Harmion自体がなくても取り出せることを重視する。
- 20〜30年の利用を視野に入れるが、実装、通信方式、暗号方式を同期間固定することは目標にしない。
- 初期用途はテキスト。将来の非テキスト対応を妨げない識別・参照・本文の拡張余地を残す。具体的なバイナリ保存方式は未決定。
- 想定ノード数は最大5台程度、同時に起動する端末は通常1〜2台。Android、Linux、Windowsなどと、Cloudflare上のHTTPノードを想定する。
- 全ノードはローカルの読み書きを受理する。分断中も作業でき、更新が行き渡れば競合集合と通常表示が収束することを目標とする。
- Cloudflareは接続しやすいレプリカであり、更新の正当性を決めるprimaryではない。Cloudflare側で本文を読めることは許容する。
- 初期版は全Contentの複製を前提とし、部分同期は扱わない。

## 2. 責任の境界

| 対象 | Harmion | アプリ・周辺ツール |
|---|---|---|
| Content | 保存、取得、更新、削除、同期、競合の保持 | 内容、kind、属性の意味 |
| データ利用 | Query、Subscribe、アクセス制御 | Queryの選択、表示、編集、計算結果の利用 |
| Interpreter | ローカルの登録・発見・呼び出し仲介・認可 | 実装、入力の選択、純粋な計算 |
| Wiki | Contentへのアクセスを提供 | リンク・埋め込み構文、補完、表示、式の解釈 |
| 競合解決 | 更新の因果関係と解決対象を扱う | 標準ツールで解決UIを提供。各アプリも専用UIを実装可能 |

Wiki、ledger系、takusu、MCP連携などは独立した利用アプリを想定する。WikiのデータモデルやUIを基盤全体の前提にはしない。最初の実証アプリは未確定。

OCR等はアプリの通常処理。Interpreterの利用は任意で、通常のデータアクセスだけを実装するアプリも認める。

## 3. Contentと更新

### 3.1 Content

- 作成時に永続的で一意なContent IDを発行する。内容ハッシュとは分け、本文が変わっても同一性を保つ。
- 基本要素はID、本文、kinds、アプリ用属性。
- kindと属性の意味はアプリが定義する。名前空間・スキーマの詳細規約は未確定。
- 更新・版を識別するIDとContent IDを分ける。時刻とローカルな競合番号だけを版の一意性に使わない。
- 編集時刻は因果関係の判定には使わない。

### 3.2 保存の契約

- 一回の保存で本文・複数属性・kindsを変更でき、ローカル保存は原子的に行う。
- 変更した項目と、その項目について実際に編集元・解決対象とした版を指定する。未変更項目は更新しない。
- 通常編集は実際の編集元を置き換える。競合解決は確認した複数版を明示して置き換える。
- バックグラウンドで更新を受信しただけでは、開いている編集画面の編集元や解決対象は増えない。
- 「同期で知っている更新」と「今回の編集で置き換える版」は別概念。
- 取得結果には、次の保存に必要な版の識別情報を含める。不透明な編集トークンとして返す。wire形式は実装時に定める。
- ローカルに永続化できれば保存成功とする。別ノードへの複製状況は別途確認できるようにする。
- 初期版では複数Contentをまたぐ原子的な更新を保証しない。

### 3.3 項目単位の競合

- 本文、属性の各キー、kindごとに独立して競合を判定する。
- 同時に保存した本文と属性でも、同期・解決後には別の端末の値と組み合わさることがある。
- 意味上不可分な情報は、初期版では本文など一つの競合単位にまとめる。項目間の整合性はアプリの責任。
- 属性の不存在、null値、空文字はそれぞれ区別する。属性の削除は明示操作とし、null値や空文字の保存では削除しない。保存要求で項目を省略した場合は、3.2のとおり未変更として扱う。
- 属性値としてlist（配列）を許可する。順序と重複を保持し、配列全体を一つの属性キーの競合単位とする。要素単位の自動マージは初期版では行わない。
- tags等を順序なし・重複なしとして解釈するのはアプリの責任。set型や要素単位の更新は、通常の配列とは別の将来機能として扱う。

## 4. 競合・解決・削除

### 4.1 本文・属性

- 因果的な後継があればその後継を現在の版とする。端末時計が古いことを理由に祖先へ戻さない。
- 並行した異なる値は未解決版として保持する。
- 未解決中の通常表示は編集時刻が後の版を優先し、同時刻は更新ID等で決定的に選ぶ。厳密なタイブレーク形式は未確定。
- 時計のずれによって実際の編集順と表示優先順位が異なることは許容する。非表示側も保持して選び直せる。
- 競合は保存・同期を止めない。アプリに公開する競合の存在を通常の取得結果から認識できるようにする。kind競合の公開には6.2の制限を適用する。
- 通常表示の版を編集するだけでは、他の競合版を解決したことにはしない。

### 4.2 kinds

| 操作 | 意味 |
|---|---|
| 二端末が同じkindを追加 | 所属する状態として表示する。後から両方を対象にできる因果情報は保持 |
| 両方の追加を確認して削除 | 所属しない状態に解決 |
| 削除と明示的な再追加が並行 | 所属する／しないの競合 |
| 本文だけ編集 | kindに更新を発生させない |

kindは所属の有無とその更新関係を扱う。初期に検討したカウンタ式setや追加優先setを採用したわけではない。未解決時の通常表示は他の項目と同じく後勝ち。

### 4.3 標準解決ツール

- Coreは、どの版を解決したかを処理する責任を持つ。
- 標準ツールを用意し、本文比較・編集、属性・kindの選択、削除と保持の選択をユーザーが行えるようにする。
- 標準解決ツールはHarmion付属の所有者向け管理ツールとし、管理操作を含む全権限を付与する。残っている共通祖先や復元候補の本文も扱える。
- 各アプリは公開された競合を知らせ、標準ツールへ誘導できればよい。専用の解決UIは任意。誘導によって管理ツールの権限や取得内容を呼び出し元アプリへ渡さない。
- 解決中に到着した未確認の並行更新は、解決保存で消さない。保存後も競合が残ることがある。
- Git的な三者マージは、共通祖先の本文がある場合に候補を作れる。初期版は標準ツールでマージ案を提示する範囲とする。
- 無人の自動マージは、複数ノードが別順序で実行しても収束する規則を定義してから導入する。
- rerere的な過去の解決再利用は任意の将来機能。同期の成立条件にしない。

### 4.4 Content全体の削除

- 削除は、確認したContent全体の状態を対象とする独立した操作。
- 確認済みの変更しかなければ削除済みにする。未確認の並行編集があれば削除と編集の競合にする。
- 未解決中は生存側を通常表示し、削除競合を通知する。本文等の後勝ちに対する例外。
- 削除前の状態を編集元とした保存は、バックグラウンド同期で削除を受信済みでも受理し、削除と編集の競合にする。保存時のアプリ認可は別途必要。
- 削除済み状態を操作の基準とする場合は、通常編集ではなく明示的な復元・解決操作とする。
- 削除競合で「削除する」は、確認した編集と削除を対象に、削除済みへ確定する。
- 削除競合で「残す」は、確認した削除を退け、本文・属性・kindsを保持する。それらの項目内にある競合まで解決したことにはしない。
- 「復元する」は、確認した削除を退け、明示的に指定した内容で復元する。削除前の内容が残っていれば管理ツールで候補として利用できるが、将来の履歴削減後も取り戻せる保証はしない。
- いずれの操作も確認した範囲だけを解決する。未確認の並行更新が後から届けば、再び競合になり得る。
- 削除記録は当初保持し続ける。長期オフライン端末から古いデータが届いても、未知の新規Contentとして復活させない。

## 5. 履歴と取得範囲

| 対象 | 初期方針 |
|---|---|
| 内部の履歴 | 全更新の本文・属性等を保持し、削減処理はまだ実装しない |
| 現在の版 | 認可の範囲で取得可能 |
| 未解決の競合版 | 認可の範囲で取得可能 |
| 任意の過去版 | 一般クライアント向け取得APIを初期版では提供しない |
| マージ用の共通祖先・削除前の復元候補 | 残っている場合に、全権限を持つ付属管理ツールへ提供。一般アプリ向けの過去版取得APIとは分ける |

全履歴の永久保存は同期の成立条件にしない。版IDは識別子であり、その本文を永久に取得できる保証ではない。

将来は現在の版、未解決の競合、必要な因果情報、削除情報を維持しつつ過去の本文等を削減できる設計を目指す。安全な削減条件は未決定。共通祖先の本文がなければ自動マージを諦め、競合として保持できる。

## 6. Query・Subscribe・アプリ認可

### 6.1 読み出しと通知

- Queryは接続先ノードの現在のローカル状態を読む。クラスタ全体の最新状態を保証しない。
- 通常値に加え、アプリに公開する競合の有無を取得できる。kind競合の公開には6.2の制限を適用する。
- 初回取得とSubscribeの間で変更を取りこぼさないAPIを用意する。
- 購読再開ができない場合は再取得を要求する。通知だけを唯一の正しさの根拠にしない。
- Query APIの正本は型付きASTとする。文字列の独自Query言語は初期版で必須にしない。
- 初期の条件はand/or/not、kind所属、等値、大小比較、属性の存在を含む。配列用にcontains、contains_any、contains_allを用意する。配列全体のeqは順序を含めて比較する。
- Queryは通常表示の値を評価する。競合候補全体の検索は別機能とし、Query条件とは独立してReadのFilterを適用する。
- Contentの最終編集時刻で絞り込める。本文・各属性・各kindについて通常表示に選ばれた版の編集時刻のうち、最も後の時刻を使う。
- 結果順序にはContent IDによる決定的なタイブレークを加える。ページングは不透明なカーソルを使う。一回のQueryは固定スナップショットをページ取得し、期限切れなら取り直す。比較の型規則と具体AST形式は実装時に定める。
- 集計、join、任意コードの実行は初期Queryに含めず、アプリ・Interpreter側で扱う。

#### Subscribe

- 条件に一致するContent集合の最新状態へ追いつくための仕組みとする。途中の変更を一つ残らず配信する履歴・イベントストリームではない。
- 短時間のA→B→Cという変更をCだけにまとめてよい。重複通知を許容するが、古い通知で新しい表示へ巻き戻らない順序情報を設ける。
- upsertはContentの表示を届いた最新スナップショットへ置き換える通知。removeは以前見えていたIDを結果から外す通知で、削除・条件不一致・権限外の詳細や新しい非公開内容は渡さない。
- reset_requiredは続きから追いつけないため初期取得をやり直す通知。初期取得と購読開始の間の更新を取りこぼさず、再接続は再開カーソルまたは明示的な再取得で扱う。
- SDKの購読キャッシュが更新されても、ユーザーが編集中の本文や編集元トークンは差し替えない。
- 初期版は条件に一致する集合を購読し、上位N件の維持は含めない。並べ替えと表示件数はクライアント側で扱う。遅い購読者向けに更新を集約し、保持上限超過ではreset_requiredを返す。
- subscribe自体が固定スナップショットの初期取得と以後の追跡を開始する。snapshot_begin、snapshot_chunk、snapshot_endの後にchangesを通知する。初期取得中の更新は完了後に反映し、途中切断では初期取得をやり直す。
- 再開カーソルはノード・アプリ・条件・購読世代に結び付け、同期ログの番号とは分離する。SDKは通知を適用してからカーソルを保存する。grant変更では再取得、資格情報失効では終了して再認証を求める。
- 送信時にも権限を検査する。固定スナップショットであっても権限外になった本文を送らない。期限・順序情報の符号化・wire形式は実装時に定める。

### 6.2 権限

| 権限 | 対象 |
|---|---|
| Read<Filter> | Contentの取得、Query、未解決版の取得、Subscribe |
| Write<Filter> | 作成、変更、削除、競合解決。Readとは独立 |
| Call<Interpreter> | 指定Interpreterの呼び出し。all指定も初期案に含む |
| Provide<Interpreter> | 指定した名前のInterpreter提供元になる。複数名を列挙でき、空は全名を意味する |
| ManageApps | アプリの認可・失効等の管理操作 |
| ManageNodes | ノードの追加・退役等の管理操作 |

- Filterはall、または指定したkindsのいずれかを含む条件。Query相当の条件式は提供しない。
- 許可はContent全体に対するもの。ledgerとwiki両方のkindを持つContentは、ledger権限でwiki用属性も読める。
- kindの所属変更はContent全体の変更としてWrite権限で行う。書き手が自分の書けるContentへ別のkindを追加すると、そのkindをRead対象とするアプリにも内容が見える。これはContent全体への許可という原則の帰結であり、意図した仕様である。Write権限は、そのContentのkindsを通じた公開範囲も変更し得るものとして扱う。別アプリへ公開させたくないContentには、そのアプリが読めるkindを書き手が追加できないよう、Write権限を分ける。
- 作成は作成後、変更は変更前後、削除は削除前がWriteのFilter内にあることを原則とする。
- ReadなしのWriteでも作成は可能。既存Contentの更新には、別途渡された編集元情報が必要となる。編集元情報を持つことはRead権限の代わりにはならず、保存時のWrite検査も省略しない。情報の受け渡し形式は未決定。
- kind競合があっても、各kindの後勝ちで選んだ通常値からkindsを構成し、そのkindsでFilterを評価する。「すべての未解決候補がFilterを満たす」という以前の案は採用しない。
- 例えばwikiへの所属・非所属が競合していても、通常値が所属ならWikiアプリへContentを公開する。そのアプリには当該kind競合を公開せず、解決も許可しない。本文等の権限内の競合とは区別し、kind競合は全権限の管理ツールで解決できる。
- 通常値が非所属となり、ほかにFilterを満たすkindがなければアクセス不可となる。同期によって通常値が変わり、アクセス可否が変わることを許容する。非所属候補が残っていても所属の通常値で公開する方針であり、既に渡した内容は取り消せない。
- 保存時に認可されて保存した更新は、後からkindの並行更新が届いて権限外になっても取り消さない。以後のアクセスを、その時点の権限判定に従って制限する。
- 許可の根拠となる最後のkindを外す操作等は、より広い権限を持つ管理ツールで行う。
- 購読対象から外れた場合は、その事実だけ通知し、新しい非公開内容は渡さない。
- アプリ認可はノードローカルであり、同期しない。各ノードを認可サーバーとし、OAuth Authorization Code＋PKCE S256を使う。ローカルの認可・トークン交換とApp APIにはHTTPSを使う。ブラウザは所有者が取得したノード専用CAを明示的に信頼する。loopback HTTPはnativeアプリのcallbackに使える。ノード間通信はHTTPSまたはirohを使う。認可とトークンの契約は[App API](app-api.md)を参照。
- ノード追加やアプリ認可は通常のアプリ権限と分けたユーザーの管理操作。
- 管理ツールも通常アプリと同じApp API・SDKを使い、必要な全権限をgrantする。専用Admin APIは設けない。Read/Writeのall FilterだけではManageApps/ManageNodesを意味しない。管理権限名と細分化は初期案であり、bootstrapは通常の管理APIとは別に定める。

### 6.3 所有者とローカル管理の信頼境界

- 初期版ではOSユーザーの実行環境を信頼する。同じOSユーザーで動く悪意あるプログラムからの隔離までは保証しない。アプリ認可は、正規のAPIを通じたアクセスを制限する。
- ローカル端末のHarmionはOSユーザーごとのプロセスとして動かし、最初のノードを作成したOSユーザーをそのノードの所有者とする。所有者確認のための独自アカウント基盤やsudo・OS管理者権限を初期版の必須条件にしない。
- 初回起動時に、そのユーザー用の保存領域へノード鍵と管理用の資格情報を作る。付属管理ツールはその資格情報で管理操作を行う。
- 別のOSユーザーや、ネットワーク・localhostへ接続できるだけの相手には管理権限を与えない。資格情報の保存と管理接続を保護する具体的なOS別方式は実装時に定める。
- ノード追加・アプリ認可は所有者が管理ツールで明示的に承認する。他ノードは信頼済みノードの参加証明を検証し、ユーザーによる承認の確認は承認元ノードに委ねる。
- Cloudflare等の遠隔ノードへローカル端末のOS所有者モデルをそのまま適用しない。遠隔ノードの初期管理資格情報の受け渡しは別途具体化する。

### 6.4 ローカル管理 Web アプリ

- 所有者が起動するローカルプロセスが管理資格情報を読み、既存 SDK と App API で Harmion に接続する。ブラウザ UI は管理専用の loopback HTTPS で配信する。ブラウザにノードの管理資格情報を渡さない。
- 所有者の起動操作で短命かつ単回の起動リンクを発行する。引き換え後の管理 UI セッションは短命で、プロセス終了時に失効する。秘密はサーバーログや永続ブラウザストレージへ保存しない。認証には UI が同一オリジンの要求に明示的に添付するセッション値を使う。同じホストの別ポートへの送信を避けるため、管理セッションを Cookie で配布しない。
- loopback への到達、URL・Content ID の提示、または一般アプリの OAuth トークンでは管理セッションを発行しない。管理データの参照と操作の両方でセッションと Host・Origin を検査する。外部オリジンへの CORS は提供しない。
- UI のスクリプトとスタイルは管理アプリ自身が配信し、本文・属性・候補はテキストとして表示する。外部スクリプトとフレーム埋め込みを禁止する。
- 一般アプリからの誘導は対象 Content を開くために使う。参照・変更には所有者セッションが必要で、変更は管理 UI 上の明示操作で行う。管理プロセスは UI の個々の操作を App API に変換する。任意の App API 操作を中継する入口や、取得した候補・履歴を呼び出し元へ返す入口は設けない。
- 同一 OS ユーザー内の隔離範囲は §6.3 に従う。所有者プロセスと同等の OS アクセスを持つアプリからも保護する場合は、ノードディレクトリ・管理プロセス・ブラウザセッションを OS の別権限境界で保護する設計が必要になる。
- 管理 UI はダークテーマを標準にし、コンテンツの閲覧と競合の編集を別画面にする。状態指標は取得したノード・時刻・集計範囲を表示する。Peer の QR・接続コードは公開登録情報を運び、読み取り後に Node ID・Cluster ID・公開鍵と操作を確認してから登録する。アプリ認可は1行の要求から要求元と権限を確認し、所有者の許可操作へ進む。

## 7. Interpreter

### 7.1 意味とライフサイクル

- ローカルノード内で登録・発見・呼び出しを仲介する。遠隔ノード上のInterpreterを探して実行する保証は持たない。
- 同名の提供元は登録承認時にユーザーが選ぶ。ノード内で名前から提供元が一つに決まる。
- ProvideとCallは別権限で、どちらもRead/Writeを含意しない。呼び出しによってInterpreterにHarmionのデータアクセス権限は付与しない。
- 初回接続はアプリ開始→管理UI承認→アプリのポーリング完了に統合し、Provider登録も同じ承認で行う。`provide_names`に含まれる名前は追加承認なしでapprovedになる。
- QueryとInterpreterを組み合わせるのは呼び出し元アプリ。
- Content入力は、呼び出し元が選んだ版のスナップショット。InterpreterがIDから最新値を取り直す契約にはしない。
- 純粋性はアプリ実装が守る契約。初期版で実行サンドボックスによる強制はしない。
- 提供元の承認と現在の接続・稼働状態は分ける。未起動なら利用不能を返し、自動起動は後回し。

### 7.2 v1契約

詳細は[Interpreter v1契約](../../contracts/interpreter-v1.md)にある。以下は設計上の要点。

- 登録情報: 1〜128バイトの名前、契約バージョン（v1は1）、入力・出力スキーマ（JSON object、各64 KiB以下）、任意のデフォルトQuery。スキーマはv1ではノードが解釈せず、呼び出し元向けの宣言として扱う。
- デフォルトQueryはv1では`{"kinds": [...]}`だけを宣言できる。ノードは実行せず、呼び出し元が自分のQuery条件とANDで結合し、選んだContentのIDと編集トークンを`call`へ渡す。これによってInterpreter自身にデータアクセス権限を与えるものではない。
- 承認済みの名前はノード内で一つ。未承認の同名登録は複数あり得て、所有者が承認時に選ぶ。承認時に明示的な置換だけを許す。grantから外れた名前の登録はsupersededになる。
- 入力: 呼び出し元が固定したContentスナップショット（件数上限なし。非ストリーミングはProviderフレーム2 MiB、ストリーミングは論理128 MiBまで）と、JSONの明示入力（深さ128、要素合計32,768、128 KiB以下）。Contentは通常値だけで、編集トークン・basis・履歴・競合候補をProviderへ渡さない。ノードはQueryやSubscribeを暗黙に実行しない。
- 成功: 任意のJSON `data`（1 MiB以下）と、任意の表示用`display`（media typeと64 KiB以下の文字列）。
- 失敗: code（1〜64バイトの小文字英数字と`. _ -`）、message（1024バイト以下）、任意のdetails（256 KiB以下）。
- displayは表示専用。編集して逆変換する契約は含めない。入力のストリーミングはv1に含み、出力のストリーミング・部分応答はv1に含めない。
- 呼び出しのタイムアウトは100〜30,000 ms、省略時10,000 ms。キャンセルは呼び出し元アプリだけが行え、ノードはProviderへ通知して待機を終了する。キャンセル後の遅延応答は破棄する。
- ノード全体32件、アプリごと8件の同時呼び出し上限を設ける。

### 7.3 IPC

- App APIは証明書固定のloopback HTTPSで、`interpreter-list`・`describe`・`register`・`approve`・`call`・`call-stream`・`cancel`・`ticket`と、統合接続の`connect-list`・`connect-approve`を提供する。呼び出しには`call`、登録には`provide`、承認には`manage_apps`を要する。`connect-start`・`connect-status`・`connect-complete`は要求secretで認可する。
- Interpreter提供元はノードへアプリ資格情報付きのloopback WebSocketを開き、JSON-RPC 2.0の`interpreter.attach`で接続する。ノードは承認済み登録と現在の`provide`・`provide_names`をDBで検査する。ブラウザProviderはOAuth originの単回・30秒ticketで接続する。
- ノードからProviderへは`interpreter.invoke`要求と`interpreter.cancel`通知を送る。ストリーミング入力では`interpreter.invoke`の`stream`記述子に続けて`interpreter.invoke.chunk`と`interpreter.invoke.end`通知を送る。Providerは同じ接続でJSON-RPC結果を返す。メッセージはテキストフレーム、2 MiB以下。拡張・サブプロトコルは使わない。
- 同じProvider IDに接続できるセッションは一つ。新しい接続は古い接続を置換し、古い接続の実行中呼び出しは利用不能として終了する。未接続・再起動・提供元交代時の挙動はこの契約に従う。
- これはノード間同期の通信路とは別。ノード間をHTTPポーリングから始める方針と矛盾しない。
- 各OS、とくにAndroidでの実行・接続方式、Provider SDKの常駐方法は引き続き検証が必要。

## 8. ノード参加・識別・信頼

- 参加を承認したノードは全データを保持できる信頼済みノード。
- 各ノードが、そのノードへ接続するアプリの権限を検査する。同期先で同じアプリの認可を再現する設計ではない。
- Cluster ID、HarmionのNode ID、ノード公開鍵、接続先、表示名を区別する。
- Cluster IDはランダムな識別子とし、所有者公開鍵をIDとして使わない。初期版では独立した所有者鍵を必須にせず、OS所有者による操作と信頼済みノードの承認を使う。将来所有者鍵を導入する場合もCluster IDとは分離し、鍵交換や喪失でクラスタの同一性を変えない設計を目指す。
- Node IDは作成時に発行し、irohのEndpoint IDやHTTPS URLに依存させない。
- 通常再起動は同じNode ID。古いバックアップからの復元や鍵喪失は新Node IDで再参加する。
- 新端末が鍵を生成し、QRやファイル等で既存端末に公開鍵・接続情報を渡す。ユーザー承認後、その公開鍵に結び付いた参加証明とクラスタ情報を渡す。
- 既存の信頼済みノードから、ユーザー操作で追加・退役を承認できる初期方針。専用の中央管理ノードは設けない。
- 参加・退役情報はノード間で伝播する。これは同期しないアプリ認可とは別。
- 退役したNode IDは再承認しない。再参加は新Node ID。
- 承認元ノードが退役しても、そのノードが承認した別ノードの参加資格は原則維持する。ユーザーが個々のノードを承認したものとして信頼し、承認元の退役だけで連鎖的に取り消さない。
- 分断中の即時失効は保証しない。退役証明の維持対象・保留・確定／却下は以下の決定と参加証明の契約に従う。既に認めた参加を連鎖失効させない方針とは区別する。
- 2026-11-18の追加決定: 退役時点で確認できた参加承認は維持する。その退役で確認されていない承認は、有効なノードで再承認する。署名の発行時刻だけで退役前かを判定しない。退役証明へ維持対象を結び付け、受信順序で対象を増やさない。別端末だけが受理していた並行承認も、自動的な維持対象とはしない。
- 同時にAがBを、BがAを退役させた場合は管理上の競合として保留する。有効な第三ノードまたは所有者が確定する。受信順序で片方を選んだり、両方の退役を自動確定したりしない。保留中は対象のデータ同期・新しい管理承認を停止し、署名済み管理証拠の交換は継続する。
- 2026-11-18の追加決定: CがBを退役させた証明を知らずにAがCを退役させた場合も、Bを自動復活させない。Bを保留・データ同期停止にし、有効なノードまたは所有者が退役の確定／未確認証明の却下を明示する。これは有効な退役証明の取り消しや同じNode IDの通常再承認とは区別する。
- 実装ではクラスタ共通の初期信頼証明をjoin時に別経路確認する。各端末の秘密鍵を持つことだけではクラスタの管理権限にならない。起点のノードも退役規則に従い、常時起動する中央管理ノードにはしない。形式・保留と却下・所有者回復は[参加証明の契約](../../contracts/membership-v1.md)を参照。
- 初回参加では公開鍵を別経路で確認する。招待文字列を知っているだけで無制限に参加できる方式にはしない。

## 9. ノード間通信・同期タイミング

### 9.1 通信路

- 端末間はiroh、HTTPノードとはHTTPSを使う。同期上の意味は通信方式に依存させない。
- irohの暗号化、またはHTTPS/WSSを利用する。平文HTTPによる外部ノード通信は採用しない。
- 通信相手の本人確認とクラスタ参加資格の確認を両方行う。HTTP側の具体的なノード認証方式は未確定。
- 初期版では本文に独自の追加暗号化やクラスタ共通の保存暗号化を重ねない。
- 接続開始の向きと同期上の権利は別。端末発の接続でCloudflareと双方向に同期できればよい。

### 9.2 発見と接続状態

- 参加ノード一覧、既知の接続先、自ノードからの認証済み接続を別々に保持する。
- 初回参加で接続先を受け取り、以降は認証済みノード間で情報交換する。irohのアドレス検索や手動更新も利用候補。
- クラスタ全体で一致するオンライン一覧は必要としない。
- 接続失敗は到達不能であり、停止・分断・退役を同一視しない。
- Cloudflare不在でも、端末間に到達可能な経路があれば同期できる。すべてのネットワーク環境で直結できる保証ではない。

### 9.3 同期契機と信頼性

- 起動、復帰、ネットワーク復帰、ローカル保存、相手の更新通知、再接続、定期照合、手動操作を契機に同期する。
- 更新通知は高速化の合図。欠落しても後の状態照合で追いつく。
- 他ノードから受け取った更新も、必要な別ノードに伝える。
- 更新IDで重複を除き、再送を許容する。既知の更新だけを受信して通知を無限に繰り返さない。
- 受領応答は保存完了後に返す。同期途中の切断で再送されても二重登録しない。
- 接続失敗は間隔を延ばして再試行する。具体的な間隔は設定・検証対象。
- 不正・未対応の同期データは理由付きエラーにし、受領済みとして扱わない。
- 保存形式、同期プロトコル、Interpreter契約は別々にバージョンを管理する。

### 9.4 Cloudflareの初期運用案

- 無料運用を優先する。
- まず保存時・復帰時のHTTPS同期と、稼働中の定期照合で始める案。30〜60秒は例示であり固定仕様ではない。
- 保存先としてSQLite-backed Durable Objectを候補とする。
- WSSによる即時通知とHibernationは追加可能だが、初期版の必須機能にしない。
- 無料枠内に収まることは実測が必要。料金・割当は変更され得るため仕様には固定しない。

## 10. Exportと可搬性

- 初期版はexportを提供し、importは後回しにする。
- exportしか残らない場合の復旧は、exportからのimport機能を必要になる前に開発する方針とする。現時点で実装済みの復旧保証とはせず、別の完全バックアップ方式を先に必須とはしない。
- 通常本文をそのまま読み取れるファイルと、ID・kinds・属性などのJSONを分ける案を採用方向とする。
- 未解決の競合版、削除記録、必要なメタデータを落とさない。形式バージョンと出力範囲を明示する。
- 任意の全過去本文をexportすることは未合意。一般の過去rev取得APIを提供しない方針とも区別する。
- ネイティブの出力形式、権限、版情報の範囲は [Export v1](../../contracts/export-v1.md) に定める。
- 初期版でHarmionへ再importできる保証は持たない。第三者のプログラムで読み取れる仕様を用意する。
- ノード秘密鍵やローカルのアプリ認可を含む完全な運用バックアップは、このexportと同一視しない。バックアップ仕様は未決定。

## 11. 確認済みシナリオ

本文の共通版v0から、Aがa1、Bがb1を並行して作成する。Cloudflare S経由または端末間同期で、両方が現在の競合版になる。通常表示は編集時刻等で選ぶ。

1. Aがa1とb1を対象に解決画面を開く。
2. Bが通常表示のb1だけを編集してb2を作る。a1を解決したことにはしない。
3. Aがa1とb1を解決するr1を保存する。
4. b2がAに届く前でも後でも、r1はb2を消さない。最終的な現在の版はr1とb2。
5. 両方を確認してr2で解決し、新たな並行更新がなければ、同期後の全ノードはr2へ収束する。

同時に確認した性質:

- 本文とタイトルの別項目編集は両方反映される。
- 同一本文の並行編集は保持される。
- 同じkindの並行追加後の削除と、削除・再追加の競合を区別できる必要がある。
- 削除は未確認の並行編集を消さない。
- 再送は重複更新を作らない。

これは意味上の机上検証であり、実装テストや形式的な収束証明ではない。

## 12. 次の検討範囲

内部表現と同期の初期方式を[内部設計](domain.md)にまとめた。ユーザーによる設計委任を受けて選定した方式であり、過去の会話で明示合意した仕様と区別する。

- 不変な更新レコード、項目ごとの置き換えグラフ、Contentの存在グラフを用いる。
- 編集開始時の基準を固定する。通常編集は削除候補を置き換えず、保持・復元を暗黙に実行しない。
- 復元は確認した範囲の全体を指定し、省略した既知属性は不存在、既知kindは非所属にする。未確認の並行更新は消さない。
- 同期はノードローカルの受理ログと世代付きカーソルを使い、依存順・ページ単位で永続化してから進捗を確定する。
- 初期版の履歴は削減せず、カーソルが使えなければ全ログを再走査する。将来のチェックポイント形式は未決定。

アプリ認可と保存のトランザクション境界、編集トークン、削除・復元時の権限制限の具体化も内部設計に記載する。意味モデルの検証は実施したが、実際のDB・通信・暗号の実装検証ではない。codec、参加証明、OS別資格情報保護等は引き続き具体化が必要。

その前提で未解決の境界は [review.md](../records/review.md) に記録する。未決定事項を既存合意として扱わないこと。

全体の責任分担とコード構成は[Architectureとパッケージ構成](architecture.md)を参照。Rustの共有ノード実装を中心に、native・Cloudflareのホストと保存・通信アダプタ、クライアントSDKを分離する。実装済み範囲は[README](../../README.md)を参照。

取得・編集・競合解決・Subscribe・OAuthの具体的な契約は[App APIの契約](app-api.md)にまとめる。保存backendは端末側SQLite＋rusqlite、Cloudflare側SQLite-backed Durable Objectsを選ぶ。ライブラリ採用時の検証事項はarchitectureを参照。
