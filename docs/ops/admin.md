## 1. 方針

1. 常設の説明を置かない。状態・値・操作だけを残す。
2. 8 画面を 5 画面 + Export に減らし、承認待ちを 1 つの受信箱へ集約する。
3. （提案・今回は変更しない）認可のために端末へ戻さない。ブラウザ内のパスキーで本人確認する。現行は端末 `y` のまま。
4. 「メンバー」はノードの集合と誤解されやすいため「ノード」に統一する。クラスタの構成要素はノードで、人の集まりではない。
5. 検索は検索対象のすぐ上に置く。画面ヘッダーには画面全体の操作だけを置く。

画面構造は GitHub の設定画面に近い、左ナビ + 一覧 / 詳細 + 表組みを基本にする。Primer の見た目をそのまま持ち込むのではなく、Harmion のダークテーマに合わせる。

## 2. 画面構成

| 現在 | 提案 |
|---|---|
| 概要 | 概要 |
| 接続要求 / Peer 承認 / Interpreter 承認 | 承認（1 つの受信箱） |
| Peer / 参加状態 | ノード |
| Content / 競合解決 | Content |
| アプリ / Interpreter / 接続 | アプリ |
| Export | Export |

- **概要**: 正常・最終受信・次回同期、4 指標、要対応、ノード一覧、識別情報。説明段落と重複カードを削除。
- **承認**: 参加・接続・Provider の承認待ちを同じリストに並べる。カードには照合に必要な項目だけを出し、影響が大きい操作だけ 1 行の警告を付ける。処理済みは下の履歴へ。
- **承認確認（提案）**: 「承認」を押すと、要求の要約・Node ID / Cluster ID・影響をモーダルで確認し、パスキーで本人確認する。端末には戻らない。今回は実装せず、現行の端末確認を残す。
- **ノード**: 自分を先頭にした一覧、退役証明、同期・退役。追加は右シート（招待 / 参加）。QR を常設しない。
- **アプリ**: 接続済み、Provider、接続履歴。接続要求は承認に置き、ここでは状態だけを見る。
- **Content**: 一覧の検索は「すべて / 競合」の直上に置く。画面ヘッダーの検索は廃止。競合は本文の上のバーから解決する。

「最近の判断」は主体が曖昧なので「処理済み」にした。処理の結果（承認 / 拒否）は行に出す。

## 3. 認可フロー（提案・今回は未実装）

現状はブラウザで承認を押したあと、起動端末に `[y/N]` が出る。どの要求への `y` か分からず、先に打った `y` が次の要求を承認し得る。6 桁コードに変えても、認可のために端末へ戻る点は変わらない。

提案:

1. ブラウザのモーダルで要求の要約と影響を確認する。
2. 「パスキーで承認」を押すと、OS の WebAuthn 確認（指紋・顔・セキュリティキー）が開く。
3. サーバが assertion を検証し、要求に紐づく一度限りの認可トークンを発行して実行する。
4. 端末には戻らない。端末は起動リンクの発行と、ヘッドレス時のフォールバックだけ。

- パスキーは初回に登録する。管理 UI の状態ディレクトリに credential を保存し、ノードのデータとは分離する。
- セッション窃取だけでは R2 を完了できない。パスキーがないと認可トークンが発行されない。
- パスキーが使えない環境は、明示的に `--approval=session`（ブラウザ確認のみ）または `--approval=terminal`（ヘッドレス用コード）を選ぶ。既定にはしない。
- ヘッドレス用コードは要求に紐づく。`y` の先打ち・取り違えは起きない。
- Export と owner key の変更はパスキー必須にする。日常の承認より一段強い確認にする。

> **前提（2026-11-28）**: パスキーは現行の管理 UI 構成では動かない。WebAuthn の RP ID に IP アドレスを使えず、CA の NameConstraints が `127.0.0.1` のみであるため（[owner-auth.md §3.4](../core/owner-auth.md#34-webauthnが現在の管理uiの構成では動かない)）。`https://localhost` への移行（leaf の DNS SAN、CA の再発行と再信頼、Host ヘッダー検査）が前提で、これを roadmap の `S-4` で判定する。`S-4` の結論が出るまでは、承認手段を端末承認または SSH assertion（実装済み）のままで作り、パスキーは差し込み口だけ残す。

## 4. コピー

削除:

- h1 直下の説明、eyebrow、フッター、ワークスペース表示。
- 承認モードの常設説明（`R2` / `TTY` / `--approval`）。
- 同期の実装説明、ポーリング間隔、件数の二重表示。
- 端末の `y` とコード入力の説明。通常フローから端末を外す。
- 「最近の判断」という抽象語。

残す:

- 不可逆操作の対象・影響（退役、全データ複製、トークン発行）。
- 期限、照合に必要な Node ID / Cluster ID / 公開鍵 / Callback / 権限。
- パスキーで承認するという操作名。OS の確認が開くこと自体はボタンで分かる。
- ヘッドレス時のコード入力先。これは非自明なフォールバックなのでヘルプに残す。

用語: ノード、承認、接続、Provider、Content、Export。

## 5. 実装メモ

今回実装:

- `App.svelte`: ナビを 5 + Export に変更。SVG アイコン、上部バーのノード識別・残り時間・終了、下部の Export。`承認` の件数バッジ。
- `Overview.svelte`: ステータス行、4 指標、要対応、ノード表、識別情報。
- `Approvals.svelte`: 接続と Provider を同じカード列に統合。処理済みは表。既存の端末 `y` フローはそのまま。
- `Peers.svelte` → ノード。ノード表と、招待 / 参加を切り替える右シート。退役証明は上部バー。
- `Apps.svelte`: 接続済み、Provider、接続履歴。登録・権限変更は折りたたみへ移動。
- `Contents.svelte`: 検索を一覧の先頭、「すべて / 競合」の直上に配置。競合バー、タイトル、フッターの ID / Kind。
- `Connections.svelte` / `Interpreters.svelte`: 画面としては未使用。承認は `Approvals.svelte` に集約。
- なし: `approval.rs` / `server.rs` の認可フロー。現行の端末確認を変更しない。
- ノード参加の保留一覧を返す API がないため、参加の承認は `ノード` のコード確認フローのまま。
- ネイティブ画面では最終受信・次回同期の値がないため、`—` または「手動」を表示する。

将来（パスキーを採用する場合）:

- `approval.rs`: 端末 `Confirmer` を WebAuthn 検証に置き換える。`terminal` / `session` はフォールバックとして残す。
- `server.rs`: 承認チャレンジの発行と assertion 検証を追加。一度限りの認可トークンを R2 リクエストに付ける。
- `api.svelte.ts`: `navigator.credentials.get` を呼ぶ。credential は管理 UI の状態に保存する。
