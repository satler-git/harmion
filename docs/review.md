## 1. 確認範囲と結論

現在の会話で提供された議論、挿入された過去チャットの抜粋・引き継ぎ、およびプロジェクト要約を照合した。初回文書化後の削除・復元、認可、管理ツール、ノード退役、OSユーザーの信頼境界の合意を追記して再確認した。省略された過去チャット原文の全件調査ではない。

最新合意を優先して整理した範囲では、基本方針を両立不能にする矛盾は見つからなかった。kind競合でも通常値で認可すること、管理ツールに全権限を与えること、OSユーザーの実行環境を信頼することは決定済み。具体的な認可APIや退役証明の検証など、以下の未決定事項を解決済みとみなさない。

ユーザーの委任により[内部設計](internal-design.md)を追加し、更新・項目・存在の関係とログ同期を選定した。小規模な意味モデルと障害モデルは検証したが、正式な収束証明や本番DB・通信・認証実装のテストではない。

## 2. 過去の提案からの更新

| 論点 | 古い案・曖昧だった説明 | 最終的に採用する整理 |
|---|---|---|
| 競合表示 | 競合時の通常値をどうするか未定 | 並行版を残して時刻で後勝ち。削除競合は生存側表示 |
| kinds | カウンタ式set、追加優先setが候補 | 削除と再追加は競合。同値の追加は表示上まとめても因果情報を失わない |
| マージ | Git的な自動マージを許容 | 初期版は提案まで。無人マージの収束規則は後回し |
| 履歴保存 | 直近のみ、または全履歴で迷っていた | 初期実装は全履歴保持。永久保存を契約にしない |
| 履歴取得 | Readに過去版取得を含める説明 | 現在・未解決版のみ一般公開。共通祖先は標準ツール向けの条件付き機能 |
| 同期の因果関係 | 受信済み情報だけで更新の前後を説明 | 受信済みと、今回置き換える編集元・解決対象を区別 |
| アプリ認可 | 認可情報は同期しない | アプリ認可はローカル。ノード参加・退役情報は伝播 |
| kind競合時の認可 | 全候補がFilter内、または確実な所属のみ許可する案 | 後勝ちの通常kindsで認可。Wikiアプリには所属・非所属のkind競合を公開・解決させない |
| 管理ツール | 共通祖先を読む権限等が未定 | 付属管理ツールに管理操作を含む全権限を付与。一般アプリへ権限を引き継がない |
| 所有者確認 | 独自ユーザー認証基盤やsudo等を検討 | 初期版はOSユーザーの実行環境を信頼。同一ユーザーの悪意あるプログラムの隔離は保証外 |
| 削除と復元 | 「削除を知った後」の意味が曖昧 | 操作の基準で区別。古い編集元の保存は削除と競合。「残す」は項目内の競合を解決しない |
| ノード退役 | 承認済みの別ノードを連鎖失効するか未定 | 承認元の退役だけでは別ノードの参加資格を取り消さない |
| 保存後の認可変更 | kind変更後の保存済み操作の扱いが未定 | 認可されて保存した更新は取り消さず、以後のアクセスを制限する |
| ReadなしのWrite | 既存更新の利用方法が未定 | 作成は可能。既存更新には別途渡された編集元情報が必要。Readの代用にはせずWrite検査も行う |
| 属性の空値と削除 | 不存在、null、空文字が未区別 | それぞれ区別し、削除は明示操作。保存要求での省略は未変更 |
| 管理ツールのAPI | 別Admin APIとAdminPrincipalを設計 | 同じApp APIとAppPrincipalを使い、管理権限を含む全grantを与える |
| OAuth | 採用未定、独自資格情報の受け渡しを先行する案 | 各ノードでAuthorization Code＋PKCEを採用する方向。所有者確認はOSの信頼と分離 |
| Cluster ID | 所有者公開鍵をIDにする案を検討 | ランダムIDを維持。独立した所有者鍵は初期必須にせず、将来追加してもIDとは分ける |
| 配列属性 | JSON相当の値とのみ記載 | 順序・重複を保持する配列を許可し、属性キー全体で競合。setの自動マージは含めない |
| Query | 言語・基本演算子が未定 | 型付きAST、論理条件・所属・比較・存在・配列包含、通常値評価、IDのタイブレーク、不透明なページカーソル |
| Subscribe | 通知を全変更の履歴配信とするか曖昧 | 最新状態への追従。中間更新の集約を許し、upsert/remove/reset_requiredで扱う |
| Interpreterの名前 | 同名提供元の選択が未整理 | ユーザーの承認時にノード内で一つに割り当てる |
| Interpreter実行 | 遠隔実行・自動起動などの構想 | ローカル仲介、未起動なら利用不能。自動起動は後回し |
| 出力 | Typed dataとstring、逆変換も候補 | 構造化dataと任意display。初期displayは表示専用 |
| Cloudflare接続 | WSSとHibernationを初期候補に提示 | 無料運用優先。まずHTTPS定期同期、WSSは追加可能 |
| 可搬性 | 復元可能なダンプまで含むような説明 | まずexportを提供。復旧が必要になる前にimportを開発する方針で、現時点の復旧保証ではない |

## 3. 文書単体で確認した両立性

### 保存と同期

ローカル保存成功と複製完了を分けることで、分断中の保存と結果整合性が両立する。Cloudflareへの接続が端末発でも、Cloudflareに特別な更新決定権を与える必要はない。

### 原子的な保存と項目ごとの解決

一回のローカル保存を途中状態として見せないことと、同期後に項目ごとの異なる版を組み合わせることは別の保証。文書では明示的に分離した。項目間の不変条件までは保証しない。

### 競合解決と後着更新

解決が確認した版だけを対象とするため、受信タイミングによって未確認更新が消えない。通常編集も同じ原則を使う。

### 全履歴と将来の削減

初期実装で全履歴を保持しても、任意の過去版の取得を契約しなければ将来削減できる。ただし本文を捨てられることと因果情報を捨てられることは別で、安全な削減条件は未定義。

### 独立したアプリと標準ツール

アプリに解決UIの実装を強制せず、全権限を持つ付属管理ツールで解決できる。一般アプリに非公開のkind競合や、残っている共通祖先・復元候補も管理ツールが扱う。一般アプリからの誘導は権限委譲を意味しない。

### kindの通常値と認可

通常値を選ぶ規則を認可にも使う。非所属候補が残っていても通常値が所属ならContentを公開し、同期で通常値が変わればアクセス可否も変わる。全候補を検査する旧案より公開を許容する意図的な変更であり、過去に渡した内容は取り消せない。一般的な競合通知の記述にはkind競合の公開制限を明記した。

### 所有者と管理権限

ローカルノードを作成したOSユーザーを所有者とし、その実行環境を信頼する。独立したユーザー認証基盤を持たずに管理操作を承認できる一方、同じOSユーザーの悪意あるプログラムから資格情報を隔離する保証はしない。別ユーザーや単に接続できる相手への認証は引き続き必要。遠隔ノードの初期設定は別途具体化する。

### 暗号化と信頼

通信暗号化を必須としても、参加済みCloudflareレプリカが本文を読むことは矛盾しない。iroh中継リレーと、データを保持するHarmionレプリカは役割が異なる。

## 4. 残る境界・注意点（新たな確定仕様ではない）

| 論点 | なぜ未解決か | 今後決めること |
|---|---|---|
| kind競合と管理操作のAPI | 内部設計で不透明なトークン、kind競合の管理ツール限定、削除状態のFilter評価を選定 | wire形式と権限別の応答・エラーの実装検証 |
| 認可検査と保存の実装 | 内部設計で認可・仮適用・保存を同一トランザクションにする | 実DBで同期更新との競合を検証 |
| Writeのみのアプリの編集元情報 | ローカルに永続化する不透明な編集トークンを選定 | 受け渡しAPI、トークンのGC・移植 |
| 削除と復元の内部表現 | 項目と存在の二つのグラフを選定し、小規模モデルで並行操作を検証 | より大きい生成ケース、実DB、将来の履歴削減との互換性 |
| 属性操作のAPI形式 | set/unsetと構造化キーを選定 | 具体codec、数値精度・同値比較規則 |
| ノード退役と承認の検証 | 承認済みノードの連鎖失効はしない方針。退役と並行・退役後の承認の判定は未定 | 参加・退役証明の検証、鍵変更。別ノードの資格維持と、新たな承認の受理条件を区別する |
| OAuthと管理権限 | nativeはHTTPSを採用し、所有者が専用CAを信頼する。実装範囲は[実装レビューのR22](implementation-review.md#r22-native-oauth)を参照 | 遠隔ノードの初期設定、対象ブラウザとクライアントライブラリの互換性 |
| Exportからのimport | 必要になる前に開発する方針で、形式・復旧手順は未定 | ID・競合・削除情報の復元、既存クラスタへの取込みと全ノード喪失時の復旧の区別。古いノードのデータから何を再送できるか |
| Exportの権限と範囲 | v1の所有者向け出力は通常値・未解決候補・削除記録を含む | アプリ向け出力の権限、全履歴や運用バックアップの形式は引き続き別途検討する。[Export v1](../contracts/export-v1.md) |
| Android・HTTP無料枠 | 接続、常駐、CPU、保存量は設計だけでは確定しない | 小さな実装での検証。無料継続や常時バックグラウンド同期は保証しない |
| Queryの評価・ページング | 型付きASTと基本演算子は合意済み | 固定スナップショットは合意済み。不在/null、異なる型・数値・配列要素の比較、上限とASTのwire形式を実装時に確定する |
| Subscribe | 最新状態へ追いつく意味と通知種別は合意済み | 初期スナップショット、上位N件なし、通知集約・上限超過でresetは合意済み。順序情報・期限・wire形式と認可変更時の実装を検証する |
| 上限・形式のバージョン | 黙って切り捨てない方針だけがある | サイズ、件数、未対応版との接続、移行手順 |

表では初期設計で選定した部分と、なお未決定・未検証の部分を区別している。

### 今回の設計検証

- 10シナリオ、計492通りの到着順に対し、依存が揃ってから受理するモデルと集合から計算する現在候補が一致した。各更新の再送も検査した。
- 解決中の追加編集、本文競合を残すタイトル編集、削除競合中の通常編集、keepとdelete、時計逆転、kindの並行追加・削除・再追加、既知属性を消す復元、未知の並行属性の保持、並行復元・削除を確認した。
- ページcommit前の失敗、ACK喪失、epoch変更後の再走査、連番の欠番、不正依存、同IDの内容不一致をモデルで検査した。
- A・S・Bの中継、分断後の追いつき、双方向の再転送が重複ログを増殖させないことを検査した。
- モデルは単一Content、少数の値・更新を扱う。認可・codec・容量・実際のクラッシュ耐久性・参加証明の検証は対象外。

到着順の検査は、小さい固定シナリオの全順列について行ったもの。任意の更新集合に対する形式証明や、全障害の網羅ではない。

## 5. 次回への引き継ぎ

1. まず仕様文書とこのレビューを読む。
2. 内部設計と意味モデルを読み、既存合意を維持して実装仕様を具体化する。
3. 「同期で知っている更新」と「項目の置き換え対象」を混同しない。
4. 現在・未解決版の保持と、過去本文の保存期間を分離する。
5. 分断、再送、解決中の追加更新、削除競合、長期オフライン復帰で候補を評価する。
6. [Architecture](architecture.md)の9パッケージとAPI境界を基準にコードを配置する。Interpreterの仲介と計算実装、アプリ認可とpeer参加資格、共有サービスとOS/Cloudflareホストを混同しない。

Architecture更新時の確認: 管理ツールは同じAppPrincipal・App APIを使い、Read/Writeのall Filterとは別に管理権限を持つ。専用Admin APIの旧案を削除した。Providerへ入力を渡してもReadを付与せず、SDKにもノード内部のDB・同期エンジンを持たせない。CloudflareはPeer APIと管理用App APIメソッドに初期配置を絞る。具体的なDO transaction binding、OAuthのローカル構成、bootstrapは実装時の検証事項。

今回の追記は文書間の照合のみ。配列の意味、Query AST、Subscribe、OAuthの実装テストはまだ行っていない。既存Pythonモデルの検証範囲を拡張したという意味ではない。

## 7. API・OAuth・Storage Backendの反映

[App API](app-api.md)へ取得・編集・競合解決・Subscribeの契約を整理した。再利用可能な編集トークンとrequest_idの冪等性、保存成功と通常表示の区別、Writeのみの受領結果を明記した。Subscribeは固定初期状態と以後の追跡を接続し、通知適用後にカーソルを保存する。

この時点ではOAuthライブラリとローカルHTTP/WSを検討した。native実装では、専用CAを使うloopback HTTPSとした。現行の契約は[App APIのOAuth節](app-api.md#5-oauthとローカル構成)を参照。

Storage Backendは端末SQLite＋rusqlite、CloudflareはDOのSQL APIを選定した。共通化するのはdriverではなく保存契約。正本・索引・ローカル認可状態を分け、同期対象を明示する。

今回の反映は文書の照合と既存意味モデルの再実行。OAuth、Query、Subscribe、DB adapterの実装テストを行ったものではない。
