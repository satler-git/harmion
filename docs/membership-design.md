# 複数ノードの参加・退役

現在の形式・判定規則・回復手順は[参加・退役証明v1](../contracts/membership-v1.md)を正本とする。この文書は設計中に見つかった問題と採用した対処を記録する。

## ユーザーが決めた方針

- 退役時点で確認できた参加承認を維持し、未確認だった承認は有効なノードで再承認する。別端末が先に見たという理由だけでは維持対象を増やさない。
- A→BとB→Aの退役が並行した場合は管理操作を競合として保留し、有効な第三ノードまたは所有者が確定する。
- C→Bの退役を知らずにAがCを退役させた場合も、Bを自動復活させない。保留・データ同期停止とし、有効なノードまたは所有者が退役の確定／未確認証明の却下を選ぶ。

## 到着順で決めないための構成

参加・退役・却下を、versionと用途を分けたcanonical bytesにEd25519で署名する。元bytesとIDを永続化し、管理ログとデータログのcursorを分離する。ページの一部だけ受理せず、検証・projection・cursorを同じtransactionで保存する。

退役には維持する証明IDの固定集合を付ける。複数の退役で維持対象を和集合にしない。署名の発行時刻で退役前かどうかを推測せず、同じ証明集合と同じ信頼起点から判定する。

各端末が自分の鍵をクラスタの信頼起点にする案では、自分だけ参加資格を保持するケースが生じた。そこで、通常の追加ノードは共通の初期信頼証明をjoin時に採用し、自分自身の本人確認情報とは分離した。未確認の参加承認を、自分の鍵を持つことだけで補えないことをSQLiteの回帰テストで検証する。

## 退役証明そのものが確認できなくなる場合

発行元の退役によって証明を無効とするだけでは、既に止めた対象が自動的に復帰する。相互退役だけを特別扱いしても、この問題は解決しなかった。

未却下の退役証明は、有効性が確認できなくても保留の根拠として残す。対象はデータ同期と新しい管理承認を停止する。独立した有効ノードの署名付き却下を、最も制限した状態から同時に適用していく。保留中の対象が新しい鍵を承認し、その鍵で自分を解除する循環は認めない。

有効な退役は通常の再承認で取り消さない。保留の確定では、新しい有効な退役と古い保留証明の却下を原子的に保存する。保留証明の却下だけを選ぶ場合も、対象本人以外の有効な管理権限を必要とする。

## 回復用のtrustは自動伝播させない

独立した有効ノードが残っていれば、その所有者がCLIで確定／却下する。そうしたノードが利用できない場合は、新しい回復ノードの鍵を各端末の所有者が別経路で確認する。ローカルな回復trustは保存するが、署名済み証明を転送しただけで他端末のtrustへ昇格させない。全端末へ同じ回復鍵を自動的に信用させる所有者鍵は初期仕様にないためである。

## 制限として残すもの

退役した鍵による後出しの証明と、分断中に正当に発行された後着証明を常に見分けることはできない。証拠交換を許して保留を検出する方式なので、既知の退役鍵による可用性妨害を完全には防がない。データ同期を再許可してこの問題を隠さず、所有者判断を必要とする制限として記録する。

全管理ログの再読込・署名再検証、経路変更の順序付き伝播の未実装、CLIのみの管理、鍵交換・証明圧縮の未実装は[実装全体レビュー](implementation-review.md)に記録する。
