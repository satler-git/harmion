# 参加・退役証明 v1

実装: `protocol::membership`、`node::membership_state/membership_log`、SQLite schema v5、native `membership_sync`。元の署名済みbytesを保存し、受信順序や発行時刻では参加資格を決めない。

## 信頼の起点と鍵

Cluster IDはランダムな識別子のまま。最初のノードを作ると、そのノードの自己署名された登録をクラスタ共通の初期信頼証明にする。`init --cluster`で作る追加ノードは未参加。所有者が既存ノードの登録ファイル全体を別経路で確認し、`join`で同じ初期信頼証明と連絡先を採用する。初期信頼証明は通常のPeer転送で差し替えない。

参加承認は既存の有効なノードで一度行う。追加ノード自身のjoinは連絡先・クラスタの確認であり、自分に参加資格を発行する操作ではない。接続先に対する全組合せの相互承認は不要。最初のノードが停止・退役しても、確認済み承認と他の有効な管理者によって運用できる。

Node ID、署名検証鍵、transport本人確認鍵、接続先を別の値として持つ。Ed25519の署名・strict検証はed25519-dalekに委ねる。nativeでは既存の`iroh.secret`から署名鍵も作る。HTTPS証明書をEd25519鍵として扱わない。irohのIP変更は参加資格を変えない。既存Node IDへの別鍵の置換・鍵の別Node IDへの流用は拒否する。

## 正本bytes

整数はbig-endian。ID・公開鍵・nonceは32 bytes。全体上限128 KiB、末尾にEd25519署名64 bytes。署名対象は署名自身を除く全bytes。証明IDは署名を含むbytesのSHA-256。

共通部分: `HMC\0`、u32 version=1、Cluster ID、発行Node ID、発行元署名検証鍵、nonce、u8 action tag。

| action | payload |
|---|---|
| 0 Admit | 対象Node ID、対象署名検証鍵、binding、接続先のu32 UTF-8 byte長とbytes |
| 1 Retire | 対象Node ID、u32維持件数、維持する証明IDの昇順集合 |
| 2 Dismiss | u32却下件数、却下する退役証明IDの空でない昇順集合 |

bindingはu8 tag=0ならu32長＋TLS DER（1〜65,536 bytes）、tag=1ならiroh Endpoint ID（32 bytes）。接続先は最大2,048 bytes。重複・逆順ID、未知version/tag、不正UTF-8、途中切断、余分なbytesは拒否する。codec受理だけでは署名検証・承認にはならない。独立Python fixtureでAdmit/Retireの符号化を照合する。

## 判定と保留

1. 全証明のcluster・署名を検査する。初期信頼証明または所有者がローカルに確認した回復鍵から、署名付き承認を辿れる範囲だけを扱う。未知の自己署名・相互承認だけで権限を作れない。
2. 退役証明の維持集合は固定。その対象ノードが発行した証明は、すべての未却下の退役証明で維持されていなければ承認根拠に使えない。集合を後から和集合にして拡大しない。既知の参加承認だけでなく、既に確認した退役・却下判断も維持対象に含める。
3. 退役証明が発行元の退役等によって有効と確定できなくても、その対象を自動的にactiveへ戻さない。その証明を保留の根拠にし、対象を`conflict`としてデータ提供・新しい管理承認を止める。維持集合に含まれる過去の承認は残る。相互退役もこの規則で保留する。
4. 有効な独立ノードが、保留中の証明を明示的に却下できる。対象本人の鍵や、保留中のノードが新たに承認した鍵で、自分の保留を解除できない。判定は最も制限した状態から開始し、有効な却下を同じ段階でまとめて適用して固定点まで進める。循環した解除は開始できない。
5. `confirm-retirement`は有効な発行元による新しい退役証明と、置き換えた保留証明の却下を一つのtransactionで保存する。`dismiss-retirement`は保留証明だけを却下する。有効と確定している退役証明をこれらの操作で取り消すことはできない。

状態は`active`、`retired`、`conflict`、`unconfirmed`。維持されなかった参加承認は`unconfirmed`となり、有効なノードで再承認する。保留の却下による復帰は、通常の退役Node ID再承認と区別する。

発行時刻を保証する独立サービスは使わない。そのため、退役済み鍵で後から作られた証明と、分断中の正当な後着証明を常に区別できるとは主張しない。既知鍵からの署名済み証拠によって保留が必要になる場合がある。安全側に停止して所有者へ判断を返す方式であり、退役鍵による可用性妨害まで防ぐ合意プロトコルではない。

## 転送・保存

Peer v1にrequest tag 4 MembershipStatus、5 MembershipCursor(epoch)、6 MembershipPage(epoch,after,high)、7 MembershipAccept(page)を追加する。Status/Cursor/Ack/CursorMismatchの応答は既存形式を共用し、証明ページのresponse tagは6。ページ構造は更新ログと同じだが、中身はHMC証明。証明versionは各HMCヘッダーで検査する。

ページは最大128件・元bytes合計4 MiB。管理ログとデータログのcursor表を分ける。固定highで双方向に管理証明を交換し、その後に現在の参加資格を再検査してデータを同期する。旧Peerが管理commandを理解しない場合は失敗し、管理情報を省略してデータ転送を続行しない。

署名・元bytes・projection更新・cursorのcommitは同じtransaction。ページ内の正常なprefixだけを保存しない。再送は証明IDで冪等。起動時も署名とIDを検査する。

登録済みの本人確認鍵は、退役・保留後も署名済み管理証明だけ交換できる。退役・保留した対象がデータを提供したり、新しい管理権限を得たりすることとは別。TLS接続の成立だけを参加承認とせず、データ操作ごとに送受信双方の有効性を検査する。

## 所有者による回復

有効な独立ノードがあれば、その管理CLIで保留を確定／却下する。利用できる独立ノードがない場合、新しいNode ID・鍵の回復ノードを作り、`join-recovery`で共通の初期信頼証明を確認する。その鍵を、影響を受けた各端末の所有者が`trust-recovery-peer`で別経路確認する。回復用trustはローカルに署名して保存し、Peer転送だけでは他端末のtrustに昇格させない。アプリの管理credentialも同期しない。

これは未承認の鍵が「所有者である」と自己申告して自動復旧する経路ではない。通常の管理競合がなく、自己の参加も確認済みの状態では回復用trustの追加を拒否する。確定した自己退役を回復用trustで迂回しない。

## 制限

- 登録JSONはv3。v2登録には署名検証鍵がないため、daemonから新しい登録を取得する。schema v4以前の既存Peerを無署名のまま他ノードへ紹介しない。
- データ・管理とも全ログから再構築する参照実装。署名検証も再実行する。大きな管理履歴の性能は最適化していない。
- 接続先は初回参加の手掛かり。既存のローカルな経路変更を古い証明の再送で上書きしない。リレーURL等の変更を全ノードへ順序付きで伝播する仕組みは未実装。
- 保留・回復はCLI。管理UIはない。署名鍵交換、証明の圧縮・GC、Cloudflareホストは今回の範囲外。
- 管理CLIの要求にはContent保存と同じrequest_id/元receiptの契約はない。応答喪失時はmembersで結果を確認する。Peerへの同じ証明bytesの再送は冪等だが、管理操作の再実行が常に元応答を返すわけではない。
